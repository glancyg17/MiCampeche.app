## Core Working Rules

1. **Always work from the actual current repo.** Never assume a prior working copy (local, from memory, or from an earlier chat session) is accurate — confirm against the real, current files before any non-trivial change. Re-confirmed constantly this session (the repo was re-cloned before nearly every build step, and again at the very end specifically to verify the last two build steps had actually landed rather than trusting conversational cues) — audit, don't assume, in either direction.
2. **Verify database/RLS/schema state directly against Supabase before assuming anything.** This session this caught, before anything shipped: that `businesses` has no public SELECT policy at all (a live join for Ofertas' WhatsApp CTA would have silently returned blank phone numbers for every real customer — fixed by snapshotting `seller_phone` onto `ofertas` instead, the same pattern `productos` already used), and confirmed the real, current Mexican digital-platform labor-law regime before a single line of Mandaditos code was written (see Hard "Never" Constraints).
2a. **When testing destructively against live Supabase, don't trust `BEGIN`/`ROLLBACK` alone** (unchanged from v5.0 — still the standing practice: disposable test rows, a real test, an explicit `SELECT`-verified cleanup). Used this way twice this session (the Mandaditos boost capacity trigger; confirmed clean afterward both times).
3. **Every change touching `index.html`, `css/styles.css`, `js/app.js`, `js/supabase-client.js`, or `manifest.json` MUST bump `CACHE_NAME` in `sw.js` in the same commit.** Non-negotiable. `CACHE_NAME` moved from `v82` to `v93` over the course of this session alone — treat whatever the real current value is as the only trustworthy number, never a number quoted in chat history (chat routinely re-checks it fresh before writing each new prompt, and you should too).
4. **Real account actions require a signed-in account whose phone is verified.** Unchanged — enforced both by `is_verified_writer()` at the DB layer and `runWriteGate` in the UI. Now also gates Mandadito registration and the private mandadito-report/review-nudge writes, same mechanism, no new gate invented.
5. **Validate against the real system before calling anything done.** Unchanged, and reinforced hard at the very end of this session: rather than trusting a prompt was applied because the person moved on to a new topic, chat re-cloned the repo and grepped for the actual expected code before updating this file — that's the standard to hold every time, not just when in doubt. Also extended naturally to Stripe this session — chat used the live Stripe MCP connection directly (with the founder's explicit real-time permission) to create the actual Mandadito-boost Product/Price/Payment Link in the live account.
6. **Voice/tone:** plain, warm, concrete. Spanish-first for anything user-facing. Never invent statistics or business numbers not stated by the founder.
7. **Flag before reopening a previously-killed idea** — including when a new request looks similar to a killed one but is meaningfully different. This session's clearest example: Mandaditos was flagged explicitly as resembling the already-killed "Hyperlocal Uber Eats/Rappi competitor" idea before any design work started, which is exactly what surfaced the real labor-law distinction that shaped the whole feature (see Hard "Never" Constraints and Mandaditos below).
8. **Solo-founder constraint:** every solution must be executable and reviewable by one person. Reaffirmed hard this session by the labor-law finding itself — a feature that would make the founder a legal employer with ongoing IMSS payroll obligations is disqualifying at this stage regardless of how the rest of the idea scores, independent of any monetization question.
9. **Big builds get broken into small, sequential, independently-shippable steps.** Mandaditos (registration → private feedback → paid boost, 3 steps) is the newest example, following the identical pattern Eventos monetization and multi-business profiles already set.
10. **(New this session) Chat delivers repo-file changes as a single, self-contained Claude Code prompt — never as inline edits chat applies itself.** Chat has no push access; Claude Code does. Chat's job on any repo-touching request is to read the real repo for context, then package a complete, precise prompt (exact diffs where the surrounding code is known, clear search-and-locate instructions with strong rationale where it isn't) including the CACHE_NAME bump reminder, a commit message, and a push+report-back instruction. **Exception:** Supabase schema/RLS/Edge-Function work and live Stripe account changes are live infrastructure chat has real, direct tool access to — chat keeps doing those directly, with the founder's explicit real-time permission for anything financial, and does not route them through Claude Code.
11. **(New this session) When a proposed feature resembles gig-economy work-matching, check Mexico's digital-platform labor law before designing anything.** The Dec 2024 reform to the Ley Federal del Trabajo (in force since 22 jun 2025, an IMSS enrollment pilot running since 1 jul 2025 and still active into 2026) treats any platform that matches or assigns paid physical-presence work to individuals as their employer once a worker earns roughly one minimum wage/month through it — "regardless of the type of service," not limited to ride-hailing/food delivery. This is now a standing check for any future feature in this shape, not a one-time Mandaditos concern.

## Hard "Never" Constraints

- **NEVER** make MiCampeche a party to someone else's transaction. Merchant-payment-facilitation was deliberately killed and stays killed. What IS live: Stripe Payment Links charging MiCampeche's *own* users for MiCampeche's *own* fees (five such flows now — see Monetization). MiCampeche never touches card data. This was re-examined hard this session (a real, concrete "should we take a cut of Ofertas sales" proposal got a full pros/cons discussion) and the answer held: **no cut, no deposit, no percentage, ever** — the current Ofertas model (business self-confirms a sale after being paid directly, in person) and the Mandaditos model (WhatsApp-connect only) are both deliberately, fully outside this line.
- **NEVER** build in-app task-matching, acceptance, or completion-status tracking for gig/courier work. (New this session — see Core Working Rule 11.) A directory — browse a profile, contact directly, deal and payment entirely outside the app — is fine; anything that has the app itself post a task, let a worker accept it, or track whether it's "in progress" or "done" is not, regardless of how small or informal it feels.
- **NEVER** build a public rating/review system for individuals (as opposed to businesses or content). (New this session.) Two independent reasons, either one sufficient on its own: it can't be anchored to a verified real transaction when the transaction itself deliberately happens outside the app (trivially gameable, actively misleading), and a visible performance-judging mechanic on a named individual edges toward "the platform evaluating the worker," the same fact pattern the labor-law reform above is watching for. Private-only feedback (a report that only the founder ever sees) is the correct shape instead — see Mandaditos.
- **NEVER** assume mock data represents real user behaviour.
- **NEVER** reproduce copyrighted news content. Noticias is aggregator-only: thumbnail, headline, honest short paraphrase, link out. This discipline extends to Eventos/Alertas/Noticias automated ingestion alike.
- **NEVER** add a feature that increases moderation burden without discussing capacity first.
- **NEVER** ship a change without validating it against the real system it touches.
- **NEVER** let a database policy or trigger grant a privilege it doesn't explicitly, narrowly intend to. Reused again this session for the Mandadito-boost RPC (a `SECURITY DEFINER` function doing its own ownership check rather than a raw owner-UPDATE RLS policy) — deliberately avoided the exact "owner can update their own row, no column restriction" shape that's already bitten this project twice.
- **NEVER** hardcode a specific route, schedule, or fare for Ko'ox (the city bus system) as static in-app content. (New this session.) The system has changed routes and transfer rules multiple times since its 2025 launch, driven by real public backlash each time — a static route list would confidently mislead people within months. Link to apps that track it live instead (see Transporte below).

## Architecture

**Frontend:** Plain HTML/CSS/JS, no framework, no build step. `index.html` · `css/styles.css` · `js/app.js` · `js/supabase-client.js` · `manifest.json` · `sw.js` · `.nojekyll` · `assets/icons/` · `assets/images/`

*Service worker:* unchanged mechanism (auto-updates silently, `skipWaiting()`/`clients.claim()`). `swMaybeReload()` (in `index.html`'s inline script) now also sets a `mc_just_updated` sessionStorage flag right before the actual reload, read once by `init()` afterward — see Install Nudge below.

### Pendiente — now three tabs, not two (this session)

The admin "Pendiente" modal, which already had an "Aprobaciones" tab (the original moderation queue) and a "Cancelaciones" tab (business-cancellation worklist, merged in a prior session), gained a third: **"Reportes"** — the private Mandaditos feedback inbox (see Mandaditos below). Same `PENDING_TABS` array, same `chip`-button tab bar, same per-tab fetch-on-open pattern. This was a deliberate reuse of an existing pattern specifically to avoid re-adding a fourth top-level admin menu item — the whole point of the earlier Cancelaciones-into-Pendiente merge was avoiding exactly that clutter, and it would have been easy to quietly undo that lesson by giving Mandaditos reports their own menu button instead.

Also fixed this session: after approving/rejecting one item, the queue jumps straight to the next remaining item in the same position (`advancePendingQueue`, `openPendingItem`) instead of dropping back to the list — only when the action came from an actual open detail view, not from the phone-verification inline quick-approve buttons embedded directly in the list (those correctly just refresh the list in place, unchanged).

### Ofertas — redemption model, fully redesigned this session

**Current, final state:** a customer taps "Contactar" on an Oferta, which opens WhatsApp straight to the business (prefilled message, no code, no app-side state at all) — identical in spirit to how Tienda/Clasificados already work. The business handles payment and pickup however they already would, entirely outside the app. Once actually paid, the business themselves — from a new "Ofertas activas" pill in their account menu — taps "+1 pago confirmado" on their own active oferta, behind a deliberate **two-step confirmation** (no undo, on purpose — the second tap is the safeguard against an accidental mis-tap, mirroring `confirmCancelBusinessPremium`'s existing two-step shape). That single action calls `increment_oferta_sold(p_oferta_id)`, a `SECURITY DEFINER` Postgres function that checks the caller's business actually owns that oferta, refuses once `quantity_sold >= quantity_total`, and bumps the count by exactly one. `ofertas.quantity_sold` (new column) is the only source of truth for "N de M vendidos" — there is no customer-side claim state of any kind, so there is no more "claimed but never showed up" gap: nothing is ever counted until the business themselves confirms real payment happened.

`ofertas.seller_phone` (new column) is snapshotted from the business's own phone at oferta-submission time — a live join to `businesses` was deliberately avoided (that table has no public SELECT policy at all; only "owner reads own" and admin), same reasoning `productos.seller_phone` already used.

**What this replaced:** an earlier design this same session built and shipped first — a customer "claims" an oferta, `ofertas_redemptions` auto-generates a real unique code + 48h expiry, the customer is shown a WhatsApp CTA with the code baked into the message as their "receipt." This actually worked and was tested, but the founder correctly identified the real flaw: too much idle time between claiming and showing up, with nothing forcing real commitment. `ofertas_redemptions` and its `get_ofertas_claim_counts` RPC were dropped entirely once the replacement above shipped — don't look for them, they no longer exist.

A parallel path was explored and explicitly set aside rather than built: charging the customer a deposit (flat $20, or a percentage like 7-8% with a floor/cap) at claim time, paid to MiCampeche itself (not the business), specifically to manufacture real commitment. This stays a live option to revisit — see Open Questions — but the founder chose to ship the simpler, zero-payment version first and only add friction if real no-show data ever shows it's actually needed.

### Mandaditos — new this session, three shipped steps

A directory of individual courier profiles (motorbike/bike/on-foot, general errands and small-package moving — not restaurant food delivery, which DiDi Food already covers). **Deliberately a directory, not a marketplace or job board** — see Hard "Never" Constraints for why (Mexico's Dec-2024 digital-platform labor-law reform). No task posting, no in-app acceptance, no status tracking, ever, in any future iteration of this feature.

**Step 1 — registration + the directory.** Tienda's screen gained a third sub-tab, "Mandaditos," alongside Mercado and Clasificados (see the renames below). New `mandaditos` table — plugged into the *same generic* `CONTENT_TABLES` / `SELF_EDIT_TABLES` / `MODERATION_DETAIL_FIELDS` machinery every other content type already uses, so it got Pendiente-queue moderation and "Mis publicaciones" self-editing for free, no bespoke code needed for either. Registration form: how they get around, the zona they cover, a photo, an optional bio — `display_name`/`phone` are snapshotted from the account itself, not collected as form fields (and not live-joined later, for the same public-SELECT-policy reason as `businesses`/`profiles` elsewhere). Immediately after submitting, the existing `openWhatsAppStep()` mechanism (unchanged, reused as-is) asks them to send an ID photo, a selfie, their plate, and a valid license to the founder's WhatsApp number — reviewed by hand, **never stored in the database at all**. That was a deliberate choice specifically to avoid creating a new category of sensitive-personal-data storage on top of an Aviso de Privacidad that's already flagged as needing a lawyer's review — reviewing once over WhatsApp and keeping nothing sidesteps that question entirely rather than adding to it. The directory itself shows a "Contactar por WhatsApp" button per profile (device-aware phone formatting, prefilled generic message) — no claim button, no reservation, nothing to accept.

Reachable to register from: a tip-gate CTA on the Mandaditos tab itself, and a "Quiero ser mandadito" entry in the account menu (parallels "Verificar mi negocio" exactly — pending/rejected states get their own copy in the same button; a published mandadito sees a *different* menu entry instead, see Step 3).

**Real bug caught and fixed *before* Mandaditos shipped:** the exact same "Mis negocios only reachable once you already have 2+ businesses" chicken-and-egg gap that Mandaditos' own design deliberately avoided was independently found and fixed for the *existing* multi-business feature this session — a Premium primary business with exactly one business had no UI path at all to add a second (fixed with a one-line condition change in `renderAccountSignedIn`). Unrelated to Mandaditos directly, found while working nearby.

**Step 2 — private-only feedback, no public ratings.** See Hard "Never" Constraints for the two independent reasons ratings were ruled out. Instead: tapping "Contactar" fires a best-effort, non-blocking log write (`mandadito_contacts` — mandadito_id, contacted_by, timestamp, resolved flag) that never blocks the WhatsApp link even if it fails (e.g. an unauthenticated visitor). 24 hours later, if unresolved, the next time that customer opens the app they see a quiet, private prompt — "¿Cómo te fue con [nombre]?" — "Todo bien" (dismiss) or "Tuve un problema" (a short note, sent privately). It expires unasked 48 hours after the original contact — silence is treated as fine, no explicit "expired" write needed, the query itself just stops returning it. Shown at most once per app-open, guarded against stacking on top of another open modal or the install-gate. Separately, every profile also has a standalone "Reportar" button, always available, not tied to any specific contact. Both paths write into one `mandadito_reports` table (a `source` column distinguishes `'nudge'` from `'manual'`, nothing else differs) — admin-only RLS, `reviewed_at` column, surfaced as the third Pendiente tab described above. **The mandadito themselves never sees any of this, at any point, under any circumstance.**

**Step 3 — the paid boost.** $99 MXN one-time (real Stripe Payment Link, created directly in the live account: `https://buy.stripe.com/6oU14o1A59CFgUGeiX4F205?locale=es-419`, redirects to `?paid=mandadito_boost`), a 7-day display-priority window, capacity-capped at **2** concurrent boosts platform-wide. `mandadito_boosts` (start_date/end_date generated as start_date+6) with a `BEFORE INSERT` trigger, `check_mandadito_boost_capacity`, mirroring `eventos_featured_bookings`'s exact shape (verified live: 2 overlapping boosts succeed, a 3rd correctly rejected, a non-overlapping window afterward succeeds — same disposable-test-data discipline as always). A requested window with no room goes straight into `mandadito_boost_waitlist` with **no payment at all** — mirrors `ofertas_waitlist`'s exact "joining a waitlist isn't a confirmed booking" behavior. **Deliberately switched off entirely until 5+ published mandaditos exist** ("no point until there's real supply," the founder's own framing) — a plain client-side check against `MANDADITOS.length` (the already-fetched public directory array), no new query or feature-flag infrastructure needed. Reachable via a new "Impulsar mi perfil" account-menu entry, shown only once a mandadito's own profile is published *and* the 5+ threshold is met platform-wide.

### Onboarding & Preferencias — the inline cards are gone (this session)

The old per-section "onboard card" (pinned inline at the top of a list, dismissible per-device, one per section: Eventos/Empleos/Perdidos/Reportes/Avisos/Alertas) is fully replaced by a real blocking overlay (`#tip-gate`, `maybeShowTipGate()`/`dismissTipGate()`) shown **once per device per section**, styled as an actual gate rather than a hero-like card — the founder's explicit complaint about the old version was that it read as decorative, not as something you had to actually deal with. A new **Preferencias** screen (hamburger menu) lets the person turn tips off entirely, or replay them (clears every `mc_onboard_*` localStorage key at once). This session it also picked up the **"Instalar la app"** action (moved here from being its own top-level menu item — see Burger Menu below), gated on `!isStandalone()`.

### Install Nudge — new this session

A lighter, additional nudge on top of the existing full-screen install-gate (which still fires once per browser session for any non-standalone visitor, unchanged): a self-dismissing toast (`maybeNudgeInstall()`, reusing the existing 2.4s auto-dismiss `toast()`) fires specifically after a successful sign-in (both the plain-login and the signup-then-WhatsApp-step paths), and again right after a detected app update finishes applying. The update case needed a small plumbing trick since a full page reload wipes JS state: `swMaybeReload()` (in `index.html`'s inline script) sets a `mc_just_updated` sessionStorage flag immediately before actually reloading; `init()` checks for it once on the next load and fires the nudge with a short delay, then clears the flag. Both paths no-op entirely once `isStandalone()` is true.

## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0 entries below remain valid precedent — new entries from this session follow.)*

- Stale JWT after anonymous→real conversion (`refreshSession()` needed explicitly).
- Owner-update RLS policies with no column restriction are a recurring privilege-escalation shape — fix pattern is a trigger (or, this session, a `SECURITY DEFINER` RPC that does its own ownership check instead of a raw policy) that reverts/refuses unless the session is genuinely admin.
- PL/pgSQL `raise exception` rolls back earlier writes in the same function call.
- `pgcrypto` lives in `extensions`, not `public`, on this project.
- `password_reset_requests` needs an explicit relationship name in PostgREST embeds (two FKs to `profiles`).
- FAB used `position:absolute` instead of `fixed` (long since fixed).
- Hero photo relative-path bug (long since fixed) — and as of this session, both `MiCampeche-Hero-2.jpg` and `MiCampeche-Hero-3.jpg` are **confirmed present** in `assets/images/`, resolving the open concern v5.0 flagged.
- `.nojekyll` missing its leading dot (long since fixed).
- Samsung Internet / Chromium mobile dark-mode auto-repaint — fixed with `color-scheme: light`.
- Viewport-unit drift — fixed with `position:fixed; inset:0` on `html`/`body`.
- Pull-to-refresh hijacking during horizontal scroll, and the release-time snap-down jump — both fixed.
- A WordPress site's default RSS feed can be stale even when the site is visibly active — always check `pubDate`/`lastBuildDate` directly.
- `.maybeSingle()` filtered only by an owner column, with no other uniqueness guarantee, is a latent crash — audit any other call whose uniqueness assumption might no longer hold as the schema evolves. (Directly relevant again this session: `MC.myMandadito()` and the Ofertas "Ofertas activas" fetch were both written from scratch with this lesson already applied — scoped correctly the first time.)
- A trigger whose side effect needs to write to a table the *acting session* doesn't have RLS access to needs `SECURITY DEFINER`.
- `BEGIN`/`ROLLBACK` via the chat's own SQL execution tool is not reliably safe for adversarial testing.
- Standing pattern (features found already built outside the visible session) — no new instance this session, but the discipline of checking rather than assuming caught the `businesses`-has-no-public-SELECT gap before it shipped, which is the same family of risk.
- A generic admin long-press "Editar" action does not exist in the code (only "Quitar"/reject) — still true, not built this session either.
- **(New) `businesses` has no public SELECT RLS policy at all** — only "owner reads own" and admin. Any future feature that wants to show a business's own public-facing detail (phone, name) to someone who is *not* that business's owner must snapshot the value onto the public-facing content row at write time (as `productos.seller_phone`, `ofertas.seller_phone`, and `mandaditos.phone`/`display_name` all now do) — never assume a live join will work for a non-owner reader.
- **(New) Google Play now requires apps to target Android 16 (API level 36) as of 31 August 2026** — a date that has already passed as of this writing. PWABuilder's underlying Bubblewrap template had an open, unresolved issue still targeting API 35 at the time this was checked. If/when Android Play Store submission is actually attempted, verify the packaging tool's current state first — a package built with a stale tool could be rejected outright.
