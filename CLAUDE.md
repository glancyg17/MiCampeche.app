## Architecture

**Frontend:** Plain HTML/CSS/JS, no framework, no build step. Same file list as v11.0, unchanged, plus `assets/images/MiCampeche-OG.jpg` (new, see Push Notifications & Sharing below).

### Home (Inicio) — Oferta del día and Evento, redesigned twice this session

**Oferta del día now has a real three-tier fallback**, replacing the prior "single newest live deal, no fallback" logic: (1) real (non-example) live ofertas whose `postedDs` is today; (2) if none, any real live oferta; (3) if no real oferta exists at all, examples (which — like the Ofertas tab itself — are exempt from the 7-day lifespan cap that made Home briefly show nothing at all before this fix, since the only ofertas in the system had aged past it). Within whichever tier is used, the pick is random with a slight (2:1) bias toward `tier==='premium'` sellers. This directly fixed a real, live gap: at the time this was diagnosed, Home's Oferta slot was rendering completely empty and the Evento card was collapsing to full width as a side effect, purely because the only ofertas in the database were examples that had aged past a cutoff Home's old logic didn't know to exempt them from.

**Both Oferta and Evento are now half-width photo-overlay cards** (`.dc-of-hero`/`.dc-ev-hero`), each with a small white date-badge pill over the image (for Evento) and a bottom text-overlay gradient, deliberately matching the same visual language later reused for the Eventos grid redesign (see below) — one look, three places by the end of the session (Home, Eventos featured, Eventos regular). Each card sits under its own leading header (`dashColHdr()`): a two-line stack (title, then "Ver todo ›") rather than one line, since "Oferta del día" plus "Ver todo" side by side does not fit a ~155px half-width column on a real phone.

### Eventos — rebuilt twice in direct succession this session

**Pass 1** replaced the old single-column "Destacado" full-width card + flat cramped list-row layout entirely with a 2-column CSS grid (`.tienda-grid`, the same container Mercado already uses) of a new card type (`.evtg-card`, later renamed in spirit but not in class name across pass 2): image on top (square, matching product cards), a small white date badge over the photo (mirroring Home's own Evento treatment), category, name, time/location, and — a deliberate change — **price now shows on any card that has one**, not just the featured one (the old compact list row had no room for it; this layout does). No trailing chevron, matching product cards, since the whole card is already tappable.

**Pass 2**, shipped the same session after the founder watched the grid live, replaced the *static* grid with a **row-based layout**: a date with exactly one event renders that card full width (`.evtg-row.solo`); a date with two or more renders a horizontal-scroll row (`.evtg-row`, same snap-scroll mechanics as Ofertas' `.of-list`) sized so 2 cards sit fully visible with a deliberate peek of a third, making "there's more, scroll" obvious without any extra UI. The Destacados set (capped at 2 by `activeFeaturedEventIds(2)`) uses the exact same row component — it only ever needs the "1 → full width / 2 → side by side" behavior, since it can never have a third to scroll to. Verified live on real dates (every real event currently happens to sit alone on its own date, so the solo path was confirmed directly; the multi-event row path was confirmed by temporarily injecting client-side-only duplicate events onto a real date via the browser console, screenshotting, then reloading to discard them — nothing was written to the database for this check).

**A latent, pre-existing test bug was found and fixed while verifying pass 2** — see Known Real Bugs.

### Push Notifications — moved to a real, persisted user preference this session

The admin-only, live-checked toggle described in v11.0 (`pushToggleRowHtml`/`refreshPushToggleRow`/`togglePushSubscription`, inside the Cuenta account menu) is **gone, replaced entirely**. Push is now:
- **A device-level preference** (`pushPref()`/`setPushPref()`, `localStorage` key `mc_push_enabled`), same pattern as the existing `tipsEnabled()`/`themePref()` — defaults to **on** (opt-out, not opt-in) and only ever changes on an explicit tap, so the displayed state never flickers or appears to "forget" a choice the way the old live-derived version could.
- **Shown to every signed-in account in Preferencias** (not admin-gated anymore — the mechanism was never admin-specific, only which server-side triggers fired was, and that hasn't changed: only `admin_messages` replies currently push to a regular user).
- **Reconciled, not just displayed:** `reconcilePushState()` runs once whenever a signed-in account opens Preferencias, quietly trying to make the *real* subscription match the *stored* preference (subscribing if the preference is on but no subscription exists yet and permission isn't already denied; unsubscribing if the preference is off but a stray subscription exists) — it never changes the stored preference itself, except the one case where an explicit tap on "Activadas" triggers a real permission prompt that the person then denies, which is a direct result of that same tap, not something flipping quietly on its own later.
- **One accepted, deliberate UX consequence:** because the default is on, a signed-in account's very first visit to Preferencias can silently trigger the real browser permission prompt (not a warning — this is the concrete meaning of "default on").

- **Photo cap raised from 3 to 5** (`productos`/`clasificados` DB constraint + the client form's `max`), a plain data-shape change with no other behavior change.
- **The detail view's image display was fundamentally wrong before this session and is now fixed:** it rendered photos as `background-size:cover` divs, which crops; it's now a real swipeable carousel (`pvCarouselHtml()`/`pvCarGo()`/`pvCarTo()`) of actual `<img>` tags with `object-fit:contain` (letterboxed, never cropped), a "n / N" counter, dots, and desktop-only (hover-capable-pointer-gated) prev/next arrows. ### Mascotas — a new standalone section, split out of Perdidos

**Perdidos split into two**, per the founder's own framing that the point of the app is consolidation, not a new invention, and that a pet-business directory should just mean "Mercado, filtered" rather than a new build:
- **Pets** (adoption, lost, found, sterilization/vaccination campaigns) → a new **Mascotas** section, reachable as the third Vecinos toggle (Avisos ⇄ Reportes ⇄ Mascotas), with its own new `mascotas` table (`type` one of `adopcion`/`perdido`/`encontrado`/`campana`, species/sex/age/sterilized for adoptions, `event_date` required for campaigns via its own CHECK constraint, up to 5 photos, `resolved_at` for owner-marked "adopted/found"). RLS mirrors the standard content-table shape exactly (owner-or-admin read/write, public read on `published` only), plus a `BEFORE INSERT OR UPDATE` trigger, `enforce_mascotas_write()`, that forces every non-admin insert to `pending` and — critically — treats a change to `resolved_at` alone as a special case that does **not** re-trigger moderation (any other field changing still does). A "Negocios" chip inside Mascotas shows Mercado products filtered to the existing "Mascotas" category (vets, groomers, pet stores) — no new table, no new screen, exactly the founder's own call.
- **Lost/found objects and missing persons** → moved into **Avisos** as two new categories, **Perdido** and **Encontrado**, exempted from the existing one-aviso-per-person-per-day limit (time-critical, and the limit's own partial-unique-index was rewritten to be NULL-safe in the same migration — `coalesce(category,'') not in (...)` rather than a bare `not in`, so a NULL category can never silently slip through the exemption via SQL's three-valued-logic).
- The 3 pre-existing pet-related Perdidos rows were migrated into `mascotas` by hand (a plain `INSERT ... SELECT` from `perdidos` mapping columns across), marked `is_example`. The old `perdidos` table itself is left in place, deprecated, untouched — nothing reads or writes it anymore, but no data was deleted.
- Safe-remove's cascade (`admin_remove_user`) was extended to include `mascotas` in its per-table rejection loop.
- **A real, separate security hole was found and closed while building this — see Security Hardening.** It applies to nine tables generally, not just the new one, and was found by testing the new table's own moderation guarantees (specifically: "can a verified non-admin force `status:'published'` on insert?") against a live disposable account, which is exactly the kind of question that generalized once asked.

### Pull-to-Refresh & Keyboard — two real bugs fixed together

- **Pull-to-refresh was checking the wrong scroll container.** `initPullToRefresh()` always read `.scr.on`'s `scrollTop` to decide "is this at the top?" — but Global Search's results panel (`#search-panel`, a separate absolutely-positioned overlay with its own `overflow-y:auto`) sits on top of whatever `.scr` is underneath, which never scrolls while search is open. Its `scrollTop` reading 0 made the very first upward-scroll gesture inside search results look like "already at the top," firing a pull no matter how far down the results actually were. Fixed with `pullScrollTarget()`, which checks for the visible search panel first and falls back to `.scr.on` otherwise — the gesture now tracks whichever layer the finger is actually touching, stored once at touch-start and reused through the whole gesture. The pull spinner's z-index was also raised above the search panel's, since it had been drawing underneath it the whole time — invisible even on the rare occasion the old bug did fire correctly.
- **The on-screen keyboard was resizing the page layout instead of overlaying it,** pushing the bottom nav up on Android/Chrome. Fixed with one addition to the viewport meta tag — `interactive-widget=overlays-content` — which tells supporting browsers to keep the layout viewport full-height and let the keyboard simply cover the bottom of the page. Chrome/Android-specific; iOS Safari doesn't recognize the token and would need a separate `visualViewport`-based fix if the same complaint ever surfaces there specifically — not built, not needed yet.

### Signup Error Handling — a real production failure, investigated and partially explained

A real user's account-creation attempt failed with a bare "No se pudo completar. Intenta de nuevo." (screenshot-reported). Investigation ruled out several concrete causes: no residual `auth.users`/`profiles` row existed anywhere for her exact email or phone (not a duplicate-account conflict); Supabase Auth's leaked-password protection is confirmed still off (not that); anonymous auth was broadly healthy the same day; a live reproduction with fresh disposable test data, through the real production UI, completed successfully end-to-end — this is not a universal, currently-broken feature.

**A real, separate bug was found regardless, and fixed:** `MC.signUp()` can fail at either of two structurally different steps — the actual Supabase Auth call (`sb.auth.updateUser`), or a later `profiles` table `UPDATE` — but both were returned as one undifferentiated `{error}`, and the caller always routed it through `authErrorToast()`, which only recognizes Auth-specific error message text. Any Postgres-side failure at the second step would have produced this exact same unhelpful generic message, with no way afterward to tell which step actually failed. `MC.signUp()` now returns `{error, source:'auth'|'profile'}`; `submitAuth()`'s signup branch routes each to the right toast function (`authErrorToast` vs `pgErrorToast`) accordingly.

**A real, separate misconfiguration was found too:** Supabase Auth's Site URL is still `http://localhost:3000` — see the top of this file. Not the cause of this specific failure as far as chat could tell, but real and unfixed.

**The specific person's specific root cause was never conclusively identified** — no historical server-side audit log survived to inspect (`auth.audit_log_entries` is genuinely empty on this project — Supabase doesn't retain it here in any queryable way), and chat's own clean reproduction succeeded. Rather than force a diagnosis, chat shipped what would have actually helped: a new admin-only diagnostic table, **`client_errors`** (`context`, `error_code`, `error_message`, `created_at`; insert-open to anyone including a still-anonymous session, admin-read-only, verified on disposable rows — empty as of this writing, which is itself the honest state: nothing has failed through this path since it shipped), and a new `handleSignupError()` that — whenever neither `authErrorToast` nor `pgErrorToast` recognizes the real error — logs it to that table AND opens a real "Un paso más: WhatsApp" modal (the exact same mechanism already used right after a *successful* signup) instead of leaving the person at a dead-end toast, pre-filling a WhatsApp message with their name/email/phone so the founder can act on it directly.

### WhatsApp Advisory Text Layout — a real, live-diagnosed rendering bug

The signup form's "we'll ask you to confirm by WhatsApp" advisory note was rendering as three visually broken columns instead of one flowing paragraph (screenshot-reported). Root cause, confirmed by inspecting the real live DOM: `.submit-note` is `display:flex`, and flexbox treats **every direct child** — including bare text nodes and inline tags, not just element children — as its own flex item. This one note's text (`"text before <b>bold phrase</b> text after"`) parsed into three separate top-level children of that flex row (a text run, the `<b>` element, another text run), each wrapping independently as its own narrow column. Every other `.submit-note` usage in the app is a single plain string with no embedded tags — exactly why only this one instance was ever affected. Fixed by wrapping the whole message in one `<span>`, verified live (reproduced the bug on production, patched the real DOM in a browser to confirm the fix, then confirmed the deployed result the same way afterward) before and after writing the code change.

### Security Hardening — v12

- **Self-publish bypass (fixed):** the RLS `INSERT` policies on nine content tables — `avisos`, `clasificados`, `empleos`, `eventos`, `mandaditos`, `perdidos`, `reportes`, `productos`, `ofertas` — never checked the `status` (or `is_example`) value a caller sent, only *who* was inserting. The client always sent the correct default (`status:'pending'`), so this was invisible from normal use, but a signed-in verified account could send a crafted request with `status:'published'` directly to the REST API and self-publish, bypassing moderation entirely. Closed with one generic `BEFORE INSERT` trigger function, `force_pending_on_insert()`, applied per-table: for any caller where `auth.uid()` is non-null and not an admin, it forces `status` back to `'pending'`, clears `rejection_reason`, and (on the six tables that have the column) forces `is_example` to `false`. Deliberately **not** applied to `noticias`/`alertas` (auto-publish pipelines — a different, dedicated review would be needed before touching those) or `businesses` (separate Premium flows). Verified end-to-end on a disposable account across all nine tables, plus confirming admin and service-role/SQL-editor inserts (where `auth.uid()` is null) are correctly left unrestricted, with a post-hoc leak check finding zero residual test rows.
- **`client_errors` (new table, see Signup Error Handling):** insert-open to `anon`/`authenticated` (`with check (true)`) by design — a still-anonymous session can hit a signup failure before any real identity exists — admin-only `SELECT`. Verified on disposable rows: a non-admin's `SELECT` returns zero rows regardless of what exists; admin sees everything.

## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0–v11.0 entries remain valid precedent — new entries from this session follow, marked (v12).)*

- **(v12)** **A committed build's embedded id can silently not match its own content's real hash, even after a reported-clean `npm test` run.** Found by independently re-cloning and re-running `node scripts/stamp.js --check` on a just-pushed commit — it failed, even though every actual line of code was byte-identical to what a correct re-stamp would produce (confirmed by diffing against a fresh `npm run stamp` run on the same content: only the embedded id values themselves differed). The exact mechanism behind how this happened was never conclusively pinned down. Trust a fresh, independent re-clone's own stamp check over a self-reported "ALL PASSED," especially right after a commit.
- **(v12)** **`activeFeaturedEventIds()` rotates off the real wall-clock hour (`new Date().getHours()`), not a mocked test time — a test that looks up a specific row by title-substring match, not an exact id, can silently break depending on what real hour it happens to run at.** `test-smoke.js`'s own Eventos-rotation test used `c.textContent.includes(title)` to find a specific card, but one fixture event's title ("Evento de prueba (posible copia)") contains another's ("Evento de prueba") as a substring — so depending on which hour-driven rotation combination came up, the lookup could silently grab the wrong card. This was latent through two separate Eventos-redesign commits before it actually surfaced, and only appeared consistently at certain real hours (verified: the same failure reproduced 5/5 times at one real hour, then 6/6 clean passes once fixed). Fixed by looking cards up via their exact `data-adm-rm="table|id"` attribute instead of any text match. Worth remembering for any other test that identifies DOM elements by substring-matching real content rather than a stable id/attribute.
- **(v12)** **`.submit-note` (and any other `display:flex` container built to hold "an icon plus some text") breaks the instant its text contains more than one top-level node.** Flexbox lays out every *direct child* — bare text nodes and inline tags included, not only element children — as its own independent flex item. A string like `"text <b>bold</b> more text"` inserted directly as a flex child's content (rather than wrapped in one element) becomes three separate flex items that each wrap on their own, producing a broken multi-column look with no CSS `column-count` involved at all. The fix is always the same: wrap the *entire* text payload in one element before handing it to a flex container. Every other current usage of `.submit-note` happens to be a single plain string, which is exactly why this had never surfaced before.
- **(v12)** **Pull-to-refresh (or any gesture handler that checks `.scr.on` to find "the current scrollable view") is wrong the instant a separate overlay layer (like Global Search's panel) is the thing actually visible and scrolling.** `.scr.on` reflects the screen underneath the overlay, not the overlay itself — checking the wrong element's `scrollTop` can make "scrolled deep into an overlay" register as "already at the top." The fix pattern is a small helper that checks for the known overlay(s) first and falls back to `.scr.on` — and remembering to raise any related UI (like a spinner) above that overlay's own z-index too, since the same oversight tends to affect both.
- **(v12)** **A generic, unrecognized-error toast at the single most costly point in the whole app (the front door — signup) is worse than useless: it gives the person no way to finish, and afterward gives nobody a way to find out what actually happened.** `MC.signUp()` had exactly this shape — two structurally different failure sources (a Supabase Auth error, a Postgres error from the following `profiles` update) collapsed into one generic-fallback-prone error path. The general lesson: any multi-step operation that can fail at genuinely different layers should say which layer failed, not just "it failed" — and the single most failure-prone entry point in an app deserves its own escape hatch (here: a WhatsApp modal, not a bare toast) plus real logging, not just a marginally-better message.
- **(v12)** **Any signed-in, non-admin user can insert a row with `status:'published'` directly (bypassing the client entirely) unless the table's INSERT policy explicitly rejects it.** The client always sent the correct default, so this was invisible from normal use, but nothing in the RLS policies themselves checked `status` on insert across nine tables. Fixed generically with one trigger function (`force_pending_on_insert`) applied per-table; deliberately **not** applied to `noticias`/`alertas` (auto-publish pipelines) or `businesses` (separate Premium flows) without dedicated review first. Worth checking any *new* content table against this same question before it ships: "can a non-admin insert this with a forged status/is_example, and does anything actually stop them?"
