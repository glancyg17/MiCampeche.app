## Architecture

**Frontend:** Plain HTML/CSS/JS, no framework, no build step. `index.html` · `css/styles.css` · `js/app.js` · `js/supabase-client.js` · `manifest.json` · `sw.js` · `.nojekyll` · `assets/icons/` · `assets/images/`

### Service Worker & App Updates — a real reliability gap found and fixed this session

The founder reported users staying stuck on old cached versions even after "pull down refresh" claimed they had the latest — sometimes for what felt like a day. Root-caused, not guessed at: `checkForUpdates()` only knows an update exists when the browser detects `sw.js` itself is byte-different (`updatefound`). GitHub Pages serves every static file — `sw.js` included — with a fixed `Cache-Control: max-age=600` and offers no way to override that per-file (confirmed via search, current as of this writing). Within that 10-minute window after a deploy, a check can genuinely, correctly see a stale cached copy and report "you're current" when a new version has, in fact, shipped.

**Fixed:** `navigator.serviceWorker.register('sw.js', {updateViaCache:'none'})` — tells the browser to never trust its HTTP cache when fetching `sw.js` to check for changes, closing the actual gap. **Also added:** a manual `?forceupdate=1` URL parameter that unregisters every service worker and clears all caches for the origin, then reloads clean — a real escape hatch for anyone still stuck (mainly iOS Safari, which is independently documented as unreliable about picking up service worker updates on its own, sometimes not self-correcting even after the 24-hour spec-mandated forced recheck) that's "send someone a link" instead of "ask them to delete and reinstall the whole app."

The underlying cache-first fetch strategy for the app shell, and the `mc_just_updated`/`swMaybeReload()` reload-on-safe-idle-moment mechanism, are otherwise unchanged from prior versions — the fix was specifically about *detecting* an update exists, not how updates are applied once detected.

### Stale-Snapshot-on-Back-Navigation — generalized this session

Prior versions' modal-navigation system (`mcModalPushView`/`mcModalBack`) snapshots a screen's rendered HTML the moment you navigate away from it, and backing out just replays that snapshot — fine for screens where nothing changed underneath, wrong for ones where something did (confirm an Oferta sale, then back out to a screen showing an ofertas-remaining count; resolve a Pendiente item, then back out to the account screen's badge). Last session this was patched narrowly (Pendiente→account only, via an explicit one-off callback). **This session it was generalized:** `mcModalPushView` now has a small internal map (`MC_MODAL_LIVE_REFRESH`) of screens that should always re-fetch live rather than replay a snapshot — currently `account` (→ `openAccount()`) and `bizProfile` (→ `refreshBusinessProfile()`) — so every existing and future push of either key gets the fix automatically, with zero changes needed at the individual call sites. `refreshBusinessProfile()` itself was also fixed in the same pass: it only ever re-fetched the business record, not the two lists (`bizProfilePosts`, `bizProfileActiveOfertas`) that drive the counts shown on that same screen — meaning even the one existing call site that used it (post-edit) had a latent gap, now closed.

Deliberately **not** generalized to every possible screen (e.g. `myBusinesses`) — checked first whether anything nested inside it could actually go stale (it can't: Premium upgrade/downgrade already explicitly re-opens fresh rather than relying on snapshot-restore), so it was left alone rather than "fixed" for a problem that didn't exist there.

### Destacado / Descuento — new this session, Premium-only perk on Productos

A Premium business can flag up to **2 products total** (combined, not 2-of-each) with **Destacado** and/or **Descuento**, independently — Descuento always implies Destacado (a discounted product is always also featured), but a business can choose Destacado alone.

**What was found before anything was built:** `productos.featured` already existed as a column, and `prodCardHtml` already rendered a "Destacado" badge for it — but `enforce_productos_edit` (the trigger that resets certain columns back to their prior value on every resident self-edit, alongside `id`/`submitted_by`/`created_at`/`business_id`) was also blanket-resetting `featured` on every edit, meaning no business had ever actually been able to set it themselves. This wasn't a deliberate, documented design — it reads as an earlier, incomplete build. Fixing it meant *removing* that reset from `enforce_productos_edit` rather than working around it.

**What's live now:**
- New columns: `discount_active boolean default false`, `discount_price_mxn numeric`, `discount_price_text text` (the last two mirroring the existing `price_mxn`/`price_text` dual-storage pattern).
- A new trigger, `enforce_producto_promo_cap` (fires BEFORE INSERT OR UPDATE, runs *after* `enforce_productos_edit` by trigger-name alphabetical order — deliberate, since Postgres fires same-event BEFORE triggers in name order and this one needs to see the post-reset state): non-Premium businesses get `featured`/`discount_active` silently coerced back to false (not rejected — the form never shows these fields to a non-Premium business, so reaching this path means a stale or crafted request, not a normal user action); `discount_active` without a price raises a real exception; `discount_active` always forces `featured` true; the 2-product cap is checked against `status in ('pending','published')` rows, same status-scoping convention as the existing multi-business product-count cap.
- A companion trigger on `businesses`, `clear_producto_promo_flags_on_downgrade`, unflags a business's products the moment `is_premium` flips false — so a lapsed Premium subscription doesn't leave a stale Destacado/Descuento badge showing until the business happens to edit that product again.
- All four of the above were verified live against real rows (a real non-premium business, the one real premium business) with disposable test inserts, not just read from the migration.
- Frontend: two new `seg`-type toggle fields on the Producto form (`featured`, `discount_active`), a conditional `discount_price` money-type field shown only when Descuento is on, both toggles hidden entirely for a non-Premium business (and force-reset to "No" client-side too, via `applyProductoBusinessHints`) — plus prefill support so editing an already-flagged product shows the toggles correctly.
- Display: the card badge for a discounted product reads **"¡Descuento!"**, deliberately not "¡Oferta!" — that word is already the name of a separate, heavily-documented, $99/day paid feature (see Ofertas above), and reusing it for a free Premium perk would confuse both users and future maintenance of this file. The regular price shows struck through next to the discount price, on both the card and the detail view.
- **Not built, deliberately deferred:** a live "1/2 slots used" counter in the form itself — the static note text covers the cap in words; wiring a live count would have touched more of `openPost`/`submitPost`'s business-selection flow than felt safe to guess at in the same pass. See Open Questions.

### Colonia — new this session, spans almost the entire app

**The list:** ~230 real colonias of San Francisco de Campeche, sourced from a public municipal directory (heraldo.com.mx) after an initial attempt to reconstruct it from search-result fragments proved unreliably incomplete — the actual page had to be read directly via the browser connector once the founder navigated to it, since the site 404's on direct automated fetches. Founder-reviewed and confirmed correct as a starting list. Lives as a plain hardcoded JS array (`CAMPECHE_COLONIAS`) plus a matching static `<datalist id="colonia-datalist">` in `index.html` — **not** a Supabase reference table, deliberately, to match how every other controlled vocabulary in this app already works (Producto/Clasificado/Negocio categories, Eventos categories, etc. are all plain JS arrays, not DB-backed lists). Editing the list later is a one-line JS-array edit shipped through the normal Claude Code pipeline, same as any category change.

**The picker:** a new `'colonia'` form-field type — a plain `<input type="text" list="colonia-datalist">`, which gives native type-to-filter behavior with zero new dependency (this was specifically chosen over a plain `<select>` after the founder flagged that ~230 items is much too long to scroll through, and over a custom-built JS combobox to avoid the extra maintenance surface a hand-rolled autocomplete widget would add). Submissions are validated against `CAMPECHE_COLONIAS` at submit time — typing something that isn't a real colonia blocks with a toast, so free text can't sneak back in through the new field the way it had through the old ones.

**Where it lives:** structured `colonia` fields on the business registration form, Clasificados, Avisos, Reportar, Perdidos, Empleos, and Eventos. **Productos and Ofertas do not have their own colonia field at all** — it's snapshotted automatically from the business via a trigger (`snapshot_colonia_from_business`, fires BEFORE INSERT OR UPDATE OF business_id on both tables), the same pattern already used for `business_name_snapshot`/`seller_phone` — verified live with a real insert. Two pre-existing freeform fields (`clasificados.zone`, `mandaditos.zona`) are now deprecated in favor of the new structured `colonia` column, same non-destructive cutover pattern already used for the old single-image `image_url` column: the old columns still exist, are no longer read or written anywhere, and are candidates for a future cleanup migration once things have been stable a while.

**Filtering:** a colonia filter (same searchable-input pattern) now exists on every relevant browse screen — Mercado, Clasificados, Eventos, Empleos, Avisos, Reportes, Perdidos — checked screen-by-screen for existing filter state before adding (some already had a category chip row to extend; Empleos and Avisos had no filter at all before this). "Nearby colonia" filtering was explicitly scoped out for now — a hand-curated adjacency list or real geocoding were both discussed, the founder chose exact-match only, revisit if it's ever actually missed.

**Mandaditos was deliberately left out of this whole rollout.** "Zona que cubres" is naturally multi-area for most couriers — a single-select picker doesn't fit it, and that needs its own quick decision (multi-select vs. a single "primary zone") before touching it. See Open Questions.

### Noticias & Alertas — auto-approve, this session

Both content types previously required manual approval via the Pendiente queue before publishing. **Now auto-published on ingestion** for both:

- **Alertas** is fed by two Edge Functions not previously documented anywhere in this file — `sync-alertas-seproci` (civil protection/weather) and `sync-alertas-smapac` (water service) — both were explicitly inserting `status:'pending'` regardless of the table's own column default, now changed to `status:'published'`. Alertas cards gained the admin "Quitar" removal wiring (`admRm`/`wireAdminRemove`) they were missing before this session — a real gap that only mattered once review stopped happening before publish.
- **Noticias** is fed by `sync-noticias-tribuna` and `sync-noticias-central`, both changed the same way. The trade-off here is real and was surfaced explicitly before building: the moderation screen's editable summary box is where the human-written paraphrase used to get added; `summary` is always `null` straight from the sync pipeline (by design — the pipeline never attempts to write one), so auto-approving means every noticia going forward shows headline + thumbnail + link only, forever, with no paraphrase. The founder confirmed this trade-off explicitly ("at least for now") before it shipped.
- A known-good admin safety net (Quitar) already existed for Noticias before this session; it did not for Alertas, and now does.

**Real incident found and fixed in the same area:** three published noticias showed a static "this image was hotlinked" warning graphic instead of a real photo. Root cause: the affected articles embed a photo hosted on a *third* domain (not Tribuna's own site), which silently serves a placeholder image when fetched with a `Referer` header from our domain — a normal-looking `200 OK`, not an error, so nothing in the original pipeline had any reason to suspect it. Confirmed directly (not guessed) by fetching the exact affected URLs from a live Edge Function with the correct Referer header and hashing the response — all three returned an identical file (12,890 bytes, `image/png`, one specific SHA-256). Both noticias sync functions now fetch and hash-check any candidate thumbnail with that same Referer before accepting it; a match is treated exactly like "no image found" (the pre-existing behavior for that case — the item is skipped, not published without a photo). This check is generic to *any* host serving this exact placeholder, not hardcoded to the one domain that triggered it. The three already-published bad rows were deleted.

## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0/v6.0/v7.0 entries below remain valid precedent — new entries from this session follow.)*

- Stale JWT after anonymous→real conversion (`refreshSession()` needed explicitly).
- Owner-update RLS policies with no column restriction are a recurring privilege-escalation shape — fix pattern is a trigger or a `SECURITY DEFINER` RPC that does its own ownership check instead of a raw policy.
- PL/pgSQL `raise exception` rolls back earlier writes in the same function call.
- `pgcrypto` lives in `extensions`, not `public`, on this project.
- `password_reset_requests` needs an explicit relationship name in PostgREST embeds (two FKs to `profiles`).
- Samsung Internet / Chromium mobile dark-mode auto-repaint — fixed with `color-scheme: light`. **(Updated this session):** now that a real dark theme exists, `color-scheme:dark` is deliberately set inside `[data-theme="dark"]` specifically so this old fix doesn't fight the new, deliberate dark mode.
- Viewport-unit drift — fixed with `position:fixed; inset:0` on `html`/`body`.
- `.maybeSingle()` filtered only by an owner column, with no other uniqueness guarantee, is a latent crash — audit any other call whose uniqueness assumption might no longer hold as the schema evolves.
- A trigger whose side effect needs to write to a table the *acting session* doesn't have RLS access to needs `SECURITY DEFINER`.
- `BEGIN`/`ROLLBACK` via the chat's own SQL execution tool is not reliably safe for adversarial testing.
- `businesses` has no public SELECT RLS policy at all — only "owner reads own" and admin. Any feature wanting to show a business's public-facing detail to a non-owner must snapshot the value onto the public-facing content row at write time — never assume a live join will work for a non-owner reader. **(Reinforced this session):** this is exactly why Productos/Ofertas' new `colonia` column is a trigger-driven snapshot from the business, not a live join or a value the client sends.
- **(New)** A generic class name reused across unrelated components is a real, recurring bug shape in this codebase, not a one-off: `.empty{padding:64px 30px}` (a generic "no results" empty-state style) and `.mcal-day.empty` (the calendar's "this day-of-month slot is blank" marker) share the word "empty" for two completely different meanings — `.mcal-day.empty` never reset `padding`, so it silently inherited 64px of padding meant for a totally different screen, which is what actually caused the reported "3-row gap" between calendar weeks. Fixed with an explicit `padding:0` on the more specific selector. Worth checking for the same shape (a component reusing a common word like "empty," "active," "selected," "disabled") if a future layout bug looks inexplicable from the obviously-relevant CSS alone.
- **(New)** A trigger that blanket-resets a column on every resident self-edit (like `enforce_productos_edit` did for `featured`) can silently make a feature permanently unusable without ever throwing an error — the column existed, the display code existed, nothing was broken in an obvious way, it just never worked. Worth a quick trigger-source check any time a "why doesn't this field ever save" report comes in, not just checking the form/insert code.
- **(New)** A third-party host embedded in syndicated RSS/article content can serve a hotlink-protection placeholder as a normal `200 OK` image response — indistinguishable from a real photo by status code alone, and only reproducible by fetching with the *same* Referer header a real browser on the production domain would send. A bare server-side fetch with no Referer returned the real photos in this exact case; only adding `Referer: https://micampeche.app/` reproduced the placeholder. Worth remembering for any future "an image looks wrong" report involving syndicated/third-party content.
- Google Play now requires apps to target Android 16 (API level 36) as of 31 August 2026 (already passed as of this writing). Verify the packaging tool's current state before attempting a Play Store submission.
- `productos`/`clasificados` still have the deprecated single `image_url` column, unread/unwritten, candidate for a future cleanup migration — unchanged from v7.0, still not urgent.
