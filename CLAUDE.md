### Contact/Interaction Gating — v10

Every contact mechanism in the app — Ofertas' "Contactar," Producto/Clasificado's WhatsApp/Llamar/Enviar mensaje, Mandaditos' card and detail-view WhatsApp buttons, Eventos' organizer WhatsApp/Llamar links, and the shared `contactCtaButtons()`/`contactCtaRow()` function covering Empleos, Perdidos, and Avisos — used to be a plain `<a href="https://wa.me/...">`/`tel:`/`sms:` link, reachable by anyone, signed in or not. All of them now route through a single new helper, `guardedContact(url)`, which runs the exact same `runWriteGate` check writes already use (signed in + phone-verified) and only navigates if it passes — reusing the existing sign-in-gate/verification-gate modals, whose own copy ("...antes de publicar o interactuar," "...podrás publicar e interactuar") already anticipated this before it was ever wired up to anything but writes. `guardedContact` deliberately uses `location.href` for every scheme rather than `window.open`, since a popup call made after an `await` can get blocked by strict mobile browsers (iOS Safari especially) as the async gap breaks the synchronous user-gesture chain that normally protects `window.open` from popup blockers.

As part of the same pass, Eventos' organizer detail view stopped printing the raw phone number as visible page text (`WhatsApp 981 000 0000`) — it was the one spot in the app doing this; every other contact button already just said "Contactar por WhatsApp"/"Llamar" with no number shown, so this brought Eventos in line with the rest.

**Known, deliberate limitation, not yet addressed:** this closes the UI-level path (a guest can no longer tap a button and reach someone), but the phone-ish values are still present in the client-side JS arrays fetched to render the cards in the first place — a guest opening devtools could still read them from memory. Fully closing that would mean redacting these columns at the database layer (a view or RPC per content table) for non-verified callers, which is a materially bigger, separate piece of work, flagged but not built this session.

### Profiles Privacy Fix — v10: a real leak found and closed

`profiles` — display name, phone, `is_admin`, `banned`, `phone_verification_status` — had a `SELECT` policy of bare `true`, scoped to the `public` role, meaning *anyone*, including a fully unauthenticated guest hitting the REST API directly with the anon key, could read every real user's phone number and admin/ban status. This predates this session and was found while researching the new Usuarios feature, not caused by it.

**Fixed in two deliberate steps**, executed by a chat session this file's own author wasn't present for (see Core Working Rule 1a) but has since verified directly:
- **Step 1** (`profiles_privacy_step1_display_names_and_phone_check`): two new functions, `display_names()` and `phone_already_verified()`, preserving the two legitimate reasons anything anonymous ever needed to touch `profiles` at all — showing an Aviso's author name, and signup's duplicate-phone check — without needing broad table access to do it. Confirmed live: a guest can call `display_names` and get a real name; `phone_already_verified` correctly requires a real session and 401s a guest.
- **Step 2** (`profiles_privacy_step2_lock_profiles_select`, applied after a deploy-and-settle wait and a manual click-through checklist): the actual lock — `profiles` SELECT restricted to owner-or-admin. Verified over **real HTTP with the actual public anon key**, not just role-emulated SQL: `GET /profiles` as a guest now returns zero rows; `display_names`/Avisos authorship still work; `phone_already_verified` still correctly requires a session; `GET /avisos` (an ordinary public feed) is unaffected; a signed-in regular account sees only their own row; admin still sees and can update every row (the specific recursion risk this kind of policy change tends to create, checked deliberately).

`email_for_phone` (a related, smaller idea raised during this work) was explicitly parked, not built. Rollback SQL is on hand in `docs/proposals/profiles-privacy/99-rollback.sql` if ever needed.

### Admin Safe-Remove / Restore — v10

Explicitly **not** a real SQL delete — discussed directly with the founder and resolved in favor of a reversible ban-and-hide, given the stakes of building destructive capability over real people's real data. Two pairs of `SECURITY DEFINER` functions, each with an internal `is_admin` check (the real security boundary here, since `SECURITY DEFINER` bypasses RLS entirely regardless of caller):

- **`admin_remove_user(target_user_id, msg)`**: sets `profiles.banned = true` (a column that has existed since early in the project — `is_verified_writer()` already checks `not banned` — but had never had any UI to set it before this), and cascades a `status='rejected', rejection_reason=msg` across everything of theirs currently `pending`/`published`: their own personal content (`eventos`, `clasificados`, `perdidos`, `empleos`, `reportes`, `avisos`, `mandaditos`), every business they own, and each of those businesses' own `productos`/`ofertas`. Already-`rejected` rows are left alone so an unrelated prior rejection reason isn't overwritten.
- **`admin_restore_user(target_user_id)`**: unbans only. Deliberately does **not** auto-restore any cascaded content — once unbanned, the person can edit/resubmit their own items through the existing normal flow (which already resets status to pending on edit), or admin can individually re-publish a specific business via the function below. Instant, unreviewed mass-republishing felt like the wrong default for what should be a rare, deliberate action.
- **`admin_remove_business(target_business_id, msg)`** / **`admin_restore_business(target_business_id)`**: same idea, scoped to one business (+ its own productos/ofertas) — does not touch the owning profile's ban status or their other businesses/content. A new `businesses.removed_by_admin boolean` column disambiguates "removed via this system after being live" from an ordinary declined-during-initial-verification rejection, since both otherwise share the same `status='rejected'` value.

**Known, accepted gap:** a business with a live Stripe Premium subscription isn't un-subscribed by any of this — deleting/deactivating it in the app doesn't cancel the Stripe charge, which the founder still has to do manually, exactly the same standing practice as ordinary Premium cancellation.

**A real bug found and fixed while building this:** `free_oferta_booking_on_reject` (a trigger from a prior session's Ofertas booking-lifecycle fix) had no `SET search_path` of its own and referenced `ofertas_bookings` unqualified — it had always silently relied on whatever search path the calling context happened to have, which every existing caller (ordinary PostgREST-mediated updates) simply provided by default. The very first time it fired from *inside* a new `SECURITY DEFINER` function using `SET search_path=''` (the established secure convention this project already uses elsewhere, e.g. `oferta_free_slot_available`), it broke outright with an "ofertas_bookings does not exist" error. Fixed by fully qualifying the reference and pinning its own `search_path` — pure robustness fix, no behavior change for any existing caller, verified with a real disposable insert-reject-confirm cycle before and after.

### Push Notifications — v10 infrastructure (extended in v11: now sixteen triggers)

Built generically from the start — nothing here is admin-specific except *which* triggers currently fire — because the founder was explicit that this should become a real feature for regular users too eventually, and wanted the infrastructure to reflect that now rather than needing a rebuild later.

- **Secrets**: a real VAPID keypair (generated with the standard `web-push` library) and a random shared secret, both stored in Supabase **Vault**, not a Deno environment variable — chat has no tool to set Edge Function secrets directly, and hardcoding a secret inside a Postgres function body isn't actually safe either (function source is generally catalog-readable). A single `get_push_secrets()` RPC, `EXECUTE` revoked from `anon`/`authenticated` and granted only to `service_role`, is how the (remote, stateless) Edge Function fetches both at invocation time using its automatically-provided service-role credentials.
- **`push_subscriptions`**: one row per subscribed device, keyed by `profile_id` (not admin-only) — endpoint/p256dh/auth. RLS: owner can insert/select/delete their own rows only. **(New, found this session — see Known Real Bugs)** an owner `UPDATE` policy was added after the original build shipped without one, which would have broken the client's `upsert(...,{onConflict:'endpoint'})` re-subscribe path the first time a browser re-registered an existing endpoint.
- **`notify_push(target_profile_ids uuid[], title, body, url)`**: the one function every trigger calls. Fire-and-forget via `pg_net`'s `net.http_post` (queues and returns immediately, never blocks the real transaction it's attached to), and the whole body is wrapped so *any* failure — missing secret, network hiccup, the Edge Function being down — is swallowed rather than raised, since a push notification failing must never roll back or error out the real write it's riding along on.
- **`send-push` Edge Function**: Deno, `npm:web-push`, `verify_jwt:false` (a Postgres trigger has no user JWT to present — auth is instead a custom `X-Push-Secret` header checked against the Vault-stored secret). Looks up the target profiles' subscriptions via the service-role client (bypassing RLS entirely, which is fine — nothing here is user-facing), sends to each, and cleans up (deletes) any subscription that comes back 404/410 (browser/OS has permanently revoked it).
- **Fourteen triggers**, covering the entire admin "Pendiente" surface: `status→'pending'` transitions on ten content tables (`eventos`, `productos`, `clasificados`, `ofertas`, `perdidos`, `empleos`, `reportes`, `avisos`, `mandaditos`, `businesses` — deliberately skipping `noticias`/`alertas`, which auto-publish since v8.0 and so never actually land pending), `profiles.phone_verification_status→'pending'`, and plain `AFTER INSERT` on `password_reset_requests`/`business_cancellation_reminders`/`mandadito_reports` (each of which has no status column at all — a new row *is* the pending item).
- **Client**: `sw.js` gained `push`/`notificationclick` handlers; `MC.subscribeToPush`/`unsubscribeFromPush`/`hasPushSubscription` handle the browser-side `PushManager` flow; an admin-only toggle in the account menu ("Notificaciones push," reads "Entrar"-style state via the same signed-in check) lets the founder turn it on. Confirmed working end-to-end on a real device, including a real fix along the way (see Known Real Bugs) for the status-bar badge rendering as a solid white square.
- **(v11) Sixteen triggers now:** the fourteen Pendiente triggers above + `trg_notify_admin_message` (per-user; title "Respuesta de MiCampeche" when `in_reply_to` is set, else "Mensaje de MiCampeche") + `notify_push_suggestion` (admin; "Contacto"/"Sugerencia" by `kind`). **The phone-verification trigger was rewritten:** it now fires only when the status is `pending` **and** the row has a real phone **and** (INSERT, or the phone changed, or the status just became pending), and it watches `UPDATE OF phone, phone_verification_status`. The old version fired on every anonymous visitor's auto-created profile (default `pending`, no phone) — the false "verificación pendiente" pushes — while never firing for the real event (a signup UPDATEs `phone` only). Tested with rolled-back disposable rows: anonymous insert 0 pushes, phone submit 1, identical retry 0, admin verify 0, phone change 1. **`notify_push` EXECUTE is now revoked from public/anon/authenticated** (Security Hardening).

### Text & Category Integrity — v11 (enforced in the database, for every writer)

- **`plain_text(text)`:** Facebook/Instagram "fancy text" (𝗟𝗼𝘀 𝗣𝗮𝘀𝘁𝗲𝗹𝗲𝘀, 𝐒𝐢𝐝𝐝𝐡𝐚𝐫𝐭𝐡𝐚, fullwidth, circled letters) is styled Unicode symbols, not letters — screen readers spell it out, it renders in odd fallback fonts, and it defeated search. It is deliberately **not** blanket NFKC, which would turn `º`/`ª` into `o`/`a` ("9º" → "9o") and rewrite `…`, `™`, `½` — verified those survive. A generic BEFORE INSERT/UPDATE trigger (`trg_a_plain_text`, arguments = column names) applies it to text columns on **11 tables**: eventos (title, description, location), avisos, empleos (title, description, company), perdidos (title, description, location), reportes, productos, clasificados, ofertas, mandaditos (display_name, description), noticias (headline, summary), alertas. ### Deploys & Caching — v11 (how "stale after every deploy" was fixed for good)

**Symptom:** after every push, the founder stayed on old files and had to close the app, clear browsing history and site data, and reopen it — something no user can be asked to do. Diagnosed with measurements, not guesses. Three stacked causes:
1. **Cloudflare (proxied, in front of GitHub Pages) edge-cached JS/CSS/`sw.js`** and told browsers to keep them 4 hours (`cf-cache-status: HIT/EXPIRED`, `cache-control: max-age=14400`), while HTML was *not* cached by Cloudflare (`DYNAMIC`). For minutes after each deploy, new HTML could be served alongside old JS/CSS — a mixed generation. GitHub's own Fastly CDN adds up to ~10 minutes of lag on top (observed live 2.5 minutes after a deploy: `sw.js` and `version.json` new, plain-URL HTML/JS/CSS still the previous deploy).
2. **The service worker trusted whatever it fetched at install.** `cache.addAll()` reads through the browser HTTP cache, and the first fix (`cache:'reload'`, commit `dd8d2fb`) bypassed only the *browser* cache, not Cloudflare or Fastly. A worker installing inside the stale window cached the mixed set under the new cache name and served it cache-first until the next hand-bumped `CACHE_NAME` — poisoned until the next deploy. The founder naturally opens the app right after pushing, which is exactly the bad window.
3. **The PWA `start_url` is `/?source=pwa`**, and `caches.match(request)` without `ignoreSearch` never matched it — installed-app launches fetched HTML from the network but JS from the cache (new HTML + old JS; a search button with no handler was seen live).

**The fix has four layers — all are required:**
- **Cloudflare (founder-performed):** Cache Rule **"Bypass Cache"** matching all incoming requests, no Browser TTL override; Browser Cache TTL respecting existing headers; Caching Level Standard; no Page Rules. GitHub Pages already is a CDN, so Cloudflare caching added only staleness. Verified: every file returns `DYNAMIC` with the origin's `max-age=600`. **This setting is part of the system** — if JS/CSS ever get cached at Cloudflare again the stale window returns (the layers below still prevent breakage, but updates lag).
- **One build id, stamped automatically (`scripts/stamp.js`, `npm run stamp`):** a 10-hex content hash of all shell files (`sw.js`, `index.html`, `css/styles.css`, `js/app.js`, `js/supabase-client.js`, `js/vendor/supabase.js`, `manifest.json`, with the stamps neutralised before hashing), written into `sw.js` (`const BUILD`; `CACHE_NAME='micampeche-'+BUILD`), `index.html` (`<meta name="mc-build">` and `?v=BUILD` on the css / supabase-client / app tags), `js/app.js` (`window.MC_BUILD`), `js/supabase-client.js` (`window.MC_BUILD_CLIENT`), `css/styles.css` (`--mc-build`), and a generated `version.json` (`{"build":"…"}`). Any change to any shell file changes the id, so the cache name changes automatically — the hand-bump is gone. `npm test` begins with `stamp.js --check` and **fails if stamps are stale**, so a forgotten stamp cannot ship. Deterministic and idempotent (verified).
- **`sw.js` verifies before it caches:** `precache()` fetches every shell file with `cache:'reload'`; for the five stamped files it checks that the response text **contains this build's id**. A stale CDN copy fails the check and is retried (up to 3 attempts) through a **unique URL** (`?b=BUILD-<ts>-<n>` — CDN caches key on the full URL, so only the origin can answer). If it is still not this build the whole install **fails**, the half-filled cache is deleted, and the previous worker keeps running until the browser retries at its next update check. A poisoned cache can no longer form. The fetch handler matches `{ignoreSearch:true}`, so `/?source=pwa` and `?v=BUILD` are served from cache. The worker's other duties (push, notificationclick, activate cleanup, skipWaiting/claim) are unchanged.
- **`index.html` self-heals what the worker can't catch** (inline script, marker `BUILD SELF-HEAL`): (1) *mixed builds* — if the HTML meta, `MC_BUILD`, `MC_BUILD_CLIENT` and the CSS variable disagree, rebuild immediately; (2) *stale build* — `/version.json` is fetched on a unique URL at load+3s, on foreground/online, and every 15 minutes; if it names a newer build, ask the worker to update (normal path: install → `controllerchange` → reload at the next safe moment), and if that hasn't landed in 60s, rebuild at the next safe moment (no modal/menu open, nothing focused). "Rebuild" = unregister workers + delete caches + reload on `/?b=<ts>`. Capped at **2 per session** (`sessionStorage mc_heal_count`) and once per remote build (`localStorage mc_heal_for`), so it can never loop. `?forceupdate=1` remains as the manual escape hatch.

**Regression tests (committed):** `test-sw.js` — 7 scenarios in a simulated worker: fresh CDN; stale copy recovered via unique URL; persistently stale → install fails and leaves no cache; HTTP 404 → fails; `/?source=pwa` and `?v=` served from cache; non-shell requests untouched. `test-selfheal.js` — 9 scenarios in jsdom: consistent build, mixed builds, CSS mismatch, unreadable CSS variable ignored, loop guard, newer remote build arms a rebuild, equal build does nothing, worker-already-updated does nothing destructive, modal-open defers. `npm test` = stamp check + test-sw + test-selfheal + test-smoke.

**Procedure for every deploy:** change files → `npm run stamp` → `npm test` (must be ALL PASSED) → commit → push → report the commit hash **and** `cat version.json`. Avoid pushing twice within ~15 minutes. Never hand-edit the stamped values.

**How to verify a deploy live (from a browser tool):** (a) `/version.json?t=<ts>` names the expected build; (b) fetch the shell files on a **unique URL** and confirm each contains the build id (plain URLs may lag a few minutes — expected and harmless now); (c) inside the app tab `caches.keys()` shows exactly `micampeche-<build>` with all 8 entries, and `MC_BUILD`, `MC_BUILD_CLIENT`, the meta tag, `--mc-build` and `version.json` all agree; (d) for header/CDN questions use an *uncontrolled* context (Rule 5a) — never the app page itself.

**Verified live on 23 sep (build `30e1a65c45`, commit `4e987c6`):** a from-scratch install cached all 8 files with every stamped file containing the build; a browser caught mid-window (new `sw.js`, old plain-URL files) ended fully consistent; a deliberately poisoned cache entry (a wrong-build `app.js`) triggered the self-heal, which cleared caches, reloaded on a unique URL and rebuilt a clean verified cache. Two earlier poisoning attempts did not trigger it because Chrome ran a clean copy of the versioned script from its own cache instead of the poisoned entry — nothing was broken in those runs. Not yet observed: a *real* future deploy propagating end to end — do that on the next push (Priorities).

**Honest limits:** GitHub Pages takes ~1–3 minutes to publish and its CDN can lag a few more, during which users simply stay on the previous *consistent* version; iOS may need one extra open to swap in the background (the self-heal covers stuck cases); a first-time visitor loading during a CDN-lag window can get a mixed page, which the page will try to repair twice and then leave alone; images under `assets/images/` aren't stamped, so a photo replaced under the same filename can be stale — prefer a new filename.

### Security Hardening — v11

- **`notify_push` lockdown (fixed):** it is `SECURITY DEFINER`, has no authorization of its own, and uses the Vault push secret; Supabase's default grants had left EXECUTE with PUBLIC/anon/authenticated, so anyone with the public anon key could call `/rest/v1/rpc/notify_push` and push an arbitrary title/body/URL to any profile id (ids are easy to find — public content rows expose `submitted_by`). Verified: anon and authenticated calls are denied; trigger-driven pushes (SECURITY DEFINER triggers owned by postgres) still queue. Nothing in the client ever called it.
- **Advisor snapshot (23 sep):** 28 `SECURITY DEFINER` functions were anon-executable (counted before the `notify_push` revoke). ## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0–v10.0 entries below remain valid precedent — new entries from 23 sep follow, marked (v11).)*

- Stale JWT after anonymous→real conversion (`refreshSession()` needed explicitly).
- Owner-update RLS policies with no column restriction are a recurring privilege-escalation shape — fix pattern is a trigger, a narrow RPC, or a `SECURITY DEFINER` function doing its own ownership check. **Reinforced this session**: `admin_messages` deliberately has no owner-`UPDATE` policy at all for exactly this reason — dismissal goes through a narrow RPC instead.
- PL/pgSQL `raise exception` rolls back earlier writes in the same function call.
- `pgcrypto` lives in `extensions`, not `public`, on this project.
- `password_reset_requests` needs an explicit relationship name in PostgREST embeds (two FKs to `profiles`).
- A generic class name reused across unrelated components is a real, recurring bug shape.
- A trigger that blanket-resets a column on every resident self-edit can silently make a feature permanently unusable without ever throwing an error.
- A third-party host embedded in syndicated content can serve a hotlink-protection placeholder as a normal `200 OK` response.
- `businesses` (and, as of last session, `profiles`) has no public SELECT RLS policy at all beyond owner-or-admin — the pattern for showing anyone else's data publicly is always a snapshot onto the reader's own row, never a live join, and any function needing the real state regardless of caller needs `SECURITY DEFINER` with an explicit `search_path`.
- Google Play requires apps to target Android 16 (API level 36) as of 31 August 2026 (already passed). Verify the packaging tool's current state before a Play Store submission attempt.
- `productos`/`clasificados` still have the deprecated single `image_url` column, unread/unwritten — unchanged, still not urgent.
- `enforce_producto_cap` (hard 10/2 product cap), `one_aviso_per_person_per_day`, and `one_clasificado_per_person` are all real, previously-undocumented DB-level constraints, discovered by hitting them — see v9.0.
- GitHub Pages' HTTP-level cache can still bite in practice even with `updateViaCache:'none'` plus `?forceupdate=1` — see v9.0. **(v11) Root cause found and fixed for good — see Deploys & Caching (Cloudflare edge caching + an unverified service-worker precache + the `/?source=pwa` cache miss).**
- A CSS overlay positioned via negative margin to overlap a sibling, rather than absolute-positioned within a shared fixed-height wrapper, will spill past that sibling if its content is ever taller than the negative-margin value assumes.
- **(v10)** A trigger with no `SET search_path` of its own, referencing a table unqualified, will work by accident for as long as every caller happens to share an ambient search path that includes the schema it needs — and break outright, with a confusing "relation does not exist" error, the first time something calls it from a context that doesn't (a `SECURITY DEFINER` function using `SET search_path=''`, this project's own established secure convention, is exactly such a context). `free_oferta_booking_on_reject` was exactly this shape; fixed by qualifying the reference and pinning its own search path. Worth a quick check on any *other* trigger written before this pattern was standard practice, if one of them starts failing mysteriously from a new caller.
- **(v10)** A table's RLS policy set can look complete (insert/select/delete all present) while still missing the one the client actually needs at runtime — `push_subscriptions` had no `UPDATE` policy, which is invisible until something calls `upsert()` against a row that already exists (an `onConflict` path is an update under the hood). Worth explicitly asking "does anything call `.upsert()` against this table?" when reviewing a new table's RLS, not just "are insert/select/delete covered."
- **(v10)** An app icon with no alpha channel at all (fully opaque) will make Android/Chrome's *auto-derived* monochrome notification-badge icon render as a solid, unstyled white square — indistinguishable from "the icon failed to load" at a glance, but actually just "there was never any transparency to derive a shape from." Fixed with a dedicated, real-transparency silhouette asset used only for the `badge` field (`icon` keeps the full-color asset, unaffected). Worth remembering for any future icon/asset work — a decorative or brand icon meant for badges/monochrome contexts needs to be authored with real alpha from the start, not derived from a flat opaque source after the fact.
- **(Obsolete — kept for history only)** `CACHE_NAME` bumps aren't guaranteed to be exactly +1 per qualifying commit — one commit from a prior session bumped it by 2. This whole "count the passes, check the arithmetic" concern no longer applies: `CACHE_NAME` is no longer hand-bumped — it is `'micampeche-'+BUILD`, where `BUILD` is a content hash stamped automatically by `scripts/stamp.js` (Rule #3).
- **(v11)** **`AFTER UPDATE OF <column>` triggers only fire when that column appears in the UPDATE's SET list — a change made by a BEFORE trigger doesn't count.** The phone-verification push watched `phone_verification_status`, but the real event (submitting a phone at signup) UPDATEs `phone` only, so real signups never pushed while noise fired constantly. When a trigger is meant to catch "a person did X", list the columns that X actually writes.
- **(v11)** **`handle_new_user` creates a `profiles` row for EVERY auth user, including anonymous visitors**, with `phone_verification_status` defaulting to `'pending'` and `phone` NULL. Any logic keyed on `profiles` must ask "does this row have a phone?" (registered = has a phone). Anonymous auth users older than 14 days are deleted nightly by cron, but ghosts routinely outnumber real accounts.
- **(v11)** **New Postgres functions are executable by `anon`/`authenticated` by default.** `SECURITY DEFINER` + no internal auth check + reachable at `/rest/v1/rpc/…` = anyone with the public anon key can call it (`notify_push` was exactly this). Run `get_advisors` after DDL (Rule 2b).
- **(v11)** **A sync that overwrites a column every run defeats a data-only fix.** The proeventos import wrote the feed's `CATEGORIES` (= the venue) into `eventos.category` on insert *and* on every update. Fixing rows changed nothing durable; the guard had to be a trigger (valid list + "junk never overwrites a valid value").
- **(v11)** **Styled Unicode ("fancy text") isn't letters.** Mathematical Alphanumeric Symbols (U+1D400–1D7FF) and friends defeat search, render in fallback fonts and read letter-by-letter in screen readers. NFD doesn't fold them; NFKC/NFKD does — but NFKC also rewrites `º`/`ª`, so stored text is folded per-character only inside those blocks (`plain_text`), while search uses NFKD for matching. Postgres ARE accepts `\U0001D400`-style escapes inside bracket expressions; `regexp_split_to_table(s,'')` splits by character.
- **(v11)** **`cache.addAll()` reads through the browser HTTP cache; `cache:'reload'` bypasses only the browser, not Cloudflare/Fastly; CDN edges key on the full URL (query string included) — as long as Cloudflare isn't set to ignore it.** A unique query string can only be answered by the origin. Never trust cached bytes you haven't verified contain the expected build id.
- **(v11)** **`caches.match(request)` without `{ignoreSearch:true}` misses any URL with a query string** — including the PWA `start_url` (`/?source=pwa`) and every `?v=BUILD` asset. Symptom: installed-app launches mixing network HTML with cached JS.
- **(v11)** **Diagnostic trap:** from a service-worker-controlled page, `fetch()` of a shell file returns the SW's cached copy with headers frozen at install time (Rule 5a). Measure from an uncontrolled context.
- **(v11)** **Claude Code formatting drift:** when Claude Code copied Codex text into `CLAUDE.md` some `**bold**` markers were stripped. Content identical, harmless — diff for substance, not bytes.
- **(v11)** **Node's `Request` needs an absolute URL** — when testing `sw.js` in a `vm` sandbox, wrap `Request` to resolve relative paths against a base (done in `test-sw.js`).
