### Contact/Interaction Gating — new this session

Every contact mechanism in the app — Ofertas' "Contactar," Producto/Clasificado's WhatsApp/Llamar/Enviar mensaje, Mandaditos' card and detail-view WhatsApp buttons, Eventos' organizer WhatsApp/Llamar links, and the shared `contactCtaButtons()`/`contactCtaRow()` function covering Empleos, Perdidos, and Avisos — used to be a plain `<a href="https://wa.me/...">`/`tel:`/`sms:` link, reachable by anyone, signed in or not. All of them now route through a single new helper, `guardedContact(url)`, which runs the exact same `runWriteGate` check writes already use (signed in + phone-verified) and only navigates if it passes — reusing the existing sign-in-gate/verification-gate modals, whose own copy ("...antes de publicar o interactuar," "...podrás publicar e interactuar") already anticipated this before it was ever wired up to anything but writes. `guardedContact` deliberately uses `location.href` for every scheme rather than `window.open`, since a popup call made after an `await` can get blocked by strict mobile browsers (iOS Safari especially) as the async gap breaks the synchronous user-gesture chain that normally protects `window.open` from popup blockers.

As part of the same pass, Eventos' organizer detail view stopped printing the raw phone number as visible page text (`WhatsApp 981 000 0000`) — it was the one spot in the app doing this; every other contact button already just said "Contactar por WhatsApp"/"Llamar" with no number shown, so this brought Eventos in line with the rest.

Known, deliberate limitation, not yet addressed: this closes the UI-level path (a guest can no longer tap a button and reach someone), but the phone-ish values are still present in the client-side JS arrays fetched to render the cards in the first place — a guest opening devtools could still read them from memory. Fully closing that would mean redacting these columns at the database layer (a view or RPC per content table) for non-verified callers, which is a materially bigger, separate piece of work, flagged but not built this session.

### Profiles Privacy Fix — a real leak found and closed this session

`profiles` — display name, phone, `is_admin`, `banned`, `phone_verification_status` — had a `SELECT` policy of bare `true`, scoped to the `public` role, meaning anyone, including a fully unauthenticated guest hitting the REST API directly with the anon key, could read every real user's phone number and admin/ban status. This predates this session and was found while researching the new Usuarios feature, not caused by it.

Fixed in two deliberate steps, executed by a chat session this file's own author wasn't present for (see Core Working Rule 1a) but has since verified directly:

- **Step 1** (`profiles_privacy_step1_display_names_and_phone_check`): two new functions, `display_names()` and `phone_already_verified()`, preserving the two legitimate reasons anything anonymous ever needed to touch `profiles` at all — showing an Aviso's author name, and signup's duplicate-phone check — without needing broad table access to do it. Confirmed live: a guest can call `display_names` and get a real name; `phone_already_verified` correctly requires a real session and 401s a guest.
- **Step 2** (`profiles_privacy_step2_lock_profiles_select`, applied after a deploy-and-settle wait and a manual click-through checklist): the actual lock — `profiles` SELECT restricted to owner-or-admin. Verified over real HTTP with the actual public anon key, not just role-emulated SQL: `GET /profiles` as a guest now returns zero rows; `display_names`/Avisos authorship still work; `phone_already_verified` still correctly requires a session; `GET /avisos` (an ordinary public feed) is unaffected; a signed-in regular account sees only their own row; admin still sees and can update every row (the specific recursion risk this kind of policy change tends to create, checked deliberately).

`email_for_phone` (a related, smaller idea raised during this work) was explicitly parked, not built. Rollback SQL is on hand in `docs/proposals/profiles-privacy/99-rollback.sql` if ever needed.

### Admin Safe-Remove / Restore — new this session

Explicitly not a real SQL delete — discussed directly with the founder and resolved in favor of a reversible ban-and-hide, given the stakes of building destructive capability over real people's real data. Two pairs of `SECURITY DEFINER` functions, each with an internal `is_admin` check (the real security boundary here, since `SECURITY DEFINER` bypasses RLS entirely regardless of caller):

- `admin_remove_user(target_user_id, msg)`: sets `profiles.banned = true` (a column that has existed since early in the project — `is_verified_writer()` already checks `not banned` — but had never had any UI to set it before this), and cascades a `status='rejected', rejection_reason=msg` across everything of theirs currently `pending`/`published`: their own personal content (`eventos`, `clasificados`, `perdidos`, `empleos`, `reportes`, `avisos`, `mandaditos`), every business they own, and each of those businesses' own `productos`/`ofertas`. Already-`rejected` rows are left alone so an unrelated prior rejection reason isn't overwritten.
- `admin_restore_user(target_user_id)`: unbans only. Deliberately does not auto-restore any cascaded content — once unbanned, the person can edit/resubmit their own items through the existing normal flow (which already resets status to pending on edit), or admin can individually re-publish a specific business via the function below. Instant, unreviewed mass-republishing felt like the wrong default for what should be a rare, deliberate action.
- `admin_remove_business(target_business_id, msg)` / `admin_restore_business(target_business_id)`: same idea, scoped to one business (+ its own productos/ofertas) — does not touch the owning profile's ban status or their other businesses/content. A new `businesses.removed_by_admin boolean` column disambiguates "removed via this system after being live" from an ordinary declined-during-initial-verification rejection, since both otherwise share the same `status='rejected'` value.

Known, accepted gap: a business with a live Stripe Premium subscription isn't un-subscribed by any of this — deleting/deactivating it in the app doesn't cancel the Stripe charge, which the founder still has to do manually, exactly the same standing practice as ordinary Premium cancellation.

A real bug found and fixed while building this: `free_oferta_booking_on_reject` (a trigger from a prior session's Ofertas booking-lifecycle fix) had no `SET search_path` of its own and referenced `ofertas_bookings` unqualified — it had always silently relied on whatever search path the calling context happened to have, which every existing caller (ordinary PostgREST-mediated updates) simply provided by default. The very first time it fired from inside a new `SECURITY DEFINER` function using `SET search_path=''` (the established secure convention this project already uses elsewhere, e.g. `oferta_free_slot_available`), it broke outright with an "ofertas_bookings does not exist" error. Fixed by fully qualifying the reference and pinning its own `search_path` — pure robustness fix, no behavior change for any existing caller, verified with a real disposable insert-reject-confirm cycle before and after.

### Push Notifications — new infrastructure this session, scoped to admin for now

Built generically from the start — nothing here is admin-specific except which triggers currently fire — because the founder was explicit that this should become a real feature for regular users too eventually, and wanted the infrastructure to reflect that now rather than needing a rebuild later.

- Secrets: a real VAPID keypair (generated with the standard `web-push` library) and a random shared secret, both stored in Supabase Vault, not a Deno environment variable — chat has no tool to set Edge Function secrets directly, and hardcoding a secret inside a Postgres function body isn't actually safe either (function source is generally catalog-readable). A single `get_push_secrets()` RPC, `EXECUTE` revoked from `anon`/`authenticated` and granted only to `service_role`, is how the (remote, stateless) Edge Function fetches both at invocation time using its automatically-provided service-role credentials.
- `push_subscriptions`: one row per subscribed device, keyed by `profile_id` (not admin-only) — endpoint/p256dh/auth. RLS: owner can insert/select/delete their own rows only. (New, found this session — see Known Real Bugs) an owner `UPDATE` policy was added after the original build shipped without one, which would have broken the client's `upsert(...,{onConflict:'endpoint'})` re-subscribe path the first time a browser re-registered an existing endpoint.
- `notify_push(target_profile_ids uuid[], title, body, url)`: the one function every trigger calls. Fire-and-forget via `pg_net`'s `net.http_post` (queues and returns immediately, never blocks the real transaction it's attached to), and the whole body is wrapped so any failure — missing secret, network hiccup, the Edge Function being down — is swallowed rather than raised, since a push notification failing must never roll back or error out the real write it's riding along on.
- `send-push` Edge Function: Deno, `npm:web-push`, `verify_jwt:false` (a Postgres trigger has no user JWT to present — auth is instead a custom `X-Push-Secret` header checked against the Vault-stored secret). Looks up the target profiles' subscriptions via the service-role client (bypassing RLS entirely, which is fine — nothing here is user-facing), sends to each, and cleans up (deletes) any subscription that comes back 404/410 (browser/OS has permanently revoked it).
- Fourteen triggers, covering the entire admin "Pendiente" surface: `status→'pending'` transitions on ten content tables (`eventos`, `productos`, `clasificados`, `ofertas`, `perdidos`, `empleos`, `reportes`, `avisos`, `mandaditos`, `businesses` — deliberately skipping `noticias`/`alertas`, which auto-publish since v8.0 and so never actually land pending), `profiles.phone_verification_status→'pending'`, and plain `AFTER INSERT` on `password_reset_requests`/`business_cancellation_reminders`/`mandadito_reports` (each of which has no status column at all — a new row is the pending item).
- Client: `sw.js` gained `push`/`notificationclick` handlers; `MC.subscribeToPush`/`unsubscribeFromPush`/`hasPushSubscription` handle the browser-side `PushManager` flow; an admin-only toggle in the account menu ("Notificaciones push," reads "Entrar"-style state via the same signed-in check) lets the founder turn it on. Confirmed working end-to-end on a real device, including a real fix along the way (see Known Real Bugs) for the status-bar badge rendering as a solid white square.

### In-App Admin Messaging — new this session, replaces a same-session WhatsApp version before it ever reached real use

The Usuarios panel's "Enviar mensaje" originally opened WhatsApp; before that ever shipped to real use, it was replaced with a real in-app message: a new `admin_messages` table (`profile_id`, `message`, `sent_by`, `created_at`, `dismissed_at`), RLS letting the owner read their own rows and admin insert-for-anyone/read-all, but no owner-`UPDATE` policy at all — deliberately, since an owner-update-with-no-column-restriction is a known recurring privilege-escalation shape this project already tracks (see Known Real Bugs, prior versions). Dismissal instead goes through a narrow `dismiss_admin_message(target_id)` RPC that can only ever touch `dismissed_at` on the caller's own row (verified: admin attempting to dismiss someone else's message correctly no-ops).

The recipient sees it as a real popup — `maybeShowUndismissedMessages()`/`renderNextAdminMessage()`/`dismissAdminMessagePopup()`, mirroring the exact shape of the existing `maybeShowMandaditoReviewNudge()` (same two guard checks, same shared modal), checked in `init()`. Closing via the modal's ✕ is deliberately not treated as dismissal — an unacknowledged message just reappears next time, since resurfacing beats silently losing it. A trigger (`trg_notify_admin_message`) also fires a real push to the recipient on insert, reusing the push infrastructure above verbatim — this is the first real per-user (non-admin-targeted) use of that infrastructure, arriving exactly as it was designed to accommodate.

A new below-hero row of four shortcuts — Mercado, Eventos, Mandaditos, Avisos — sits in normal document flow (scrolls away with the rest of the page, not sticky/fixed), each jumping straight to its target tab and sub-mode in one tap.
- **Phase 4 — Inicio's content feed reorganized**, in order: Special Slot (see above) → Row 1, Oferta del día (left) paired with Evento (right) in a 2-column grid that collapses to a single full-width column if either side is legitimately empty → Row 2, the Mercado Destacado carousel, now relocated to also mount on Home (one shared rotation index/timer feeds both the Mercado and Home grids, kept in sync — rotation now starts/stops based on either screen being visible, not just Mercado) → Row 3, Noticias, still exactly the two most recent articles, now side by side instead of stacked.
  - Oferta del día gained real randomization for the first time: previously always "the single newest live deal, premium-tier first, no randomness at all" — now picks randomly among live ofertas whose `postedDs` (the date it actually went live) is today, or randomly among all remaining live ones if none went live today.
  - The old separate "Evento destacado" (paid-featured, hourly-rotating) and "Eventos de hoy" (a full chronological list of everything happening today) were merged into one slot with an explicit three-tier fallback, designed so it should essentially never be empty: (1) currently-active Destacado bookings, resolved to their real underlying events and sorted so ones whose event is actually happening today outrank ones merely being promoted today for a later date — a real distinction, since a paid boost window and the event's own date aren't the same thing; (2) if no Destacado is active, today's events, any; (3) if neither, all upcoming events. The only case it can legitimately render empty is zero events existing anywhere in the system at all.

## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0–v9.0 entries below remain valid precedent — new entries from this session follow.)*

- Stale JWT after anonymous→real conversion (`refreshSession()` needed explicitly).
- Owner-update RLS policies with no column restriction are a recurring privilege-escalation shape — fix pattern is a trigger, a narrow RPC, or a `SECURITY DEFINER` function doing its own ownership check. Reinforced this session: `admin_messages` deliberately has no owner-`UPDATE` policy at all for exactly this reason — dismissal goes through a narrow RPC instead.
- PL/pgSQL `raise exception` rolls back earlier writes in the same function call.
- `pgcrypto` lives in `extensions`, not `public`, on this project.
- `password_reset_requests` needs an explicit relationship name in PostgREST embeds (two FKs to `profiles`).
- A generic class name reused across unrelated components is a real, recurring bug shape.
- A trigger that blanket-resets a column on every resident self-edit can silently make a feature permanently unusable without ever throwing an error.
- A third-party host embedded in syndicated content can serve a hotlink-protection placeholder as a normal `200 OK` response.
- `businesses` (and, as of last session, `profiles`) has no public SELECT RLS policy at all beyond owner-or-admin — the pattern for showing anyone else's data publicly is always a snapshot onto the reader's own row, never a live join, and any function needing the real state regardless of caller needs `SECURITY DEFINER` with an explicit `search_path`.
- Google Play requires apps to target Android 16 (API level 36) as of 31 August 2026 (already passed). Verify the packaging tool's current state before a Play Store submission attempt.
- `productos`/`clasificados` still have the deprecated single `image_url` column, unread/unwritten — unchanged, still not urgent.
- `enforce_producto_cap` (hard 10/2 product cap), `one_aviso_per_person_per_day`, and `one_clasificado_per_person` are all real, previously-undocumented DB-level constraints, discovered by hitting them — see v9.0.
- GitHub Pages' HTTP-level cache can still bite in practice even with `updateViaCache:'none'` plus `?forceupdate=1` — see v9.0.
- A CSS overlay positioned via negative margin to overlap a sibling, rather than absolute-positioned within a shared fixed-height wrapper, will spill past that sibling if its content is ever taller than the negative-margin value assumes.
- **(New)** A trigger with no `SET search_path` of its own, referencing a table unqualified, will work by accident for as long as every caller happens to share an ambient search path that includes the schema it needs — and break outright, with a confusing "relation does not exist" error, the first time something calls it from a context that doesn't (a `SECURITY DEFINER` function using `SET search_path=''`, this project's own established secure convention, is exactly such a context). `free_oferta_booking_on_reject` was exactly this shape; fixed by qualifying the reference and pinning its own search path. Worth a quick check on any other trigger written before this pattern was standard practice, if one of them starts failing mysteriously from a new caller.
- **(New)** A table's RLS policy set can look complete (insert/select/delete all present) while still missing the one the client actually needs at runtime — `push_subscriptions` had no `UPDATE` policy, which is invisible until something calls `upsert()` against a row that already exists (an `onConflict` path is an update under the hood). Worth explicitly asking "does anything call `.upsert()` against this table?" when reviewing a new table's RLS, not just "are insert/select/delete covered."
- **(New)** An app icon with no alpha channel at all (fully opaque) will make Android/Chrome's auto-derived monochrome notification-badge icon render as a solid, unstyled white square — indistinguishable from "the icon failed to load" at a glance, but actually just "there was never any transparency to derive a shape from." Fixed with a dedicated, real-transparency silhouette asset used only for the `badge` field (`icon` keeps the full-color asset, unaffected). Worth remembering for any future icon/asset work — a decorative or brand icon meant for badges/monochrome contexts needs to be authored with real alpha from the start, not derived from a flat opaque source after the fact.
- **(Obsolete — kept for history only)** `CACHE_NAME` bumps aren't guaranteed to be exactly +1 per qualifying commit — one commit from a prior session bumped it by 2. This whole "count the passes, check the arithmetic" concern no longer applies at all: `CACHE_NAME` is no longer hand-bumped — it's `'micampeche-'+BUILD`, where `BUILD` is a content hash stamped automatically by `scripts/stamp.js` (Rule #3). Nobody ever needs to reason about its value by hand again.
