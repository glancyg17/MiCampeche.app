### Live Visual Verification Technique — new this session

For CSS/layout bugs specifically (as opposed to logic bugs test-smoke.js can catch), chat now has a real, repeatable way to inspect the actual rendered page rather than reasoning about markup and CSS in the abstract: navigate the browser connector to `https://micampeche.app`, inject a small `<style>` override forcing `#desktop-gate{display:none}` / `#app{display:block}` (the app's own real gate, keyed on viewport width, otherwise shows a QR-code landing page to any non-mobile-width browser), then use `nav('tienda')` (or whichever screen) directly in the page's own JS console rather than trying to click through a possibly-mis-sized layout. Two real caveats discovered doing this, both worth remembering: (a) the browser tool's own output filtering blocks anything that looks like a query string or cookie, which caught legitimate `wa.me/...?text=...` hrefs embedded in card markup — read specific computed values/text content instead of dumping raw `outerHTML` when this happens; (b) a fresh page load can still be served a stale cached `app.js`/`styles.css` from the *browser's own* HTTP cache (independent of the service worker — GitHub Pages' 10-minute `max-age` header, same root cause v8.0 already documented, just discovered again from a different angle) even *after* `?forceupdate=1` — confirmed this can happen by fetching the live file directly with a cache-busting query string and comparing it to what the loaded page was actually running. When in doubt, `fetch('/js/app.js?bust='+Date.now())` and check for the expected string directly, rather than trusting whatever the currently-open tab has loaded.

Ofertas specifically also got two deliberate carve-outs so example content actually persists the way the founder asked ("these will remain until I ask you to remove them"): example ofertas are exempt from the normal 7-day lifespan filter, and are always sorted *after* every real oferta so a real business's real deal always claims the "oferta del día" hero-banner slot when at least one real oferta exists.

### Destacados — new this session, spans Premium businesses generally

A rotating promo strip at the top of Mercado (`#destacados-wrap`), pulling every currently-eligible product (`featured` or `discount_active` true, `status='published'`) across *every* Premium business, not just one — this is the direct answer to "what happens once there's more than one Premium business," since the per-business cap of 2 (`enforce_producto_promo_cap`, unchanged from last session) only ever bounded a single business's own contribution. Shows 2 at a time; if the eligible pool exceeds 2, it auto-rotates through the pool 2-at-a-time every 7 seconds (a plain client-side `setInterval`, started only while Mercado is the visible sub-tab and stopped otherwise, no server-side "whose turn" state at all). Reuses the existing `prodCardHtml` card renderer verbatim — same badges, same tap-through to detail view, same admin long-press-to-remove — this is a new *placement*, not a new card type. Separately, the in-grid Destacado/Descuento badge was redesigned from a small corner pill into a diagonal corner ribbon (reusing `.prod-badge`/`.prod-badge-discount`, restyled) for more visibility in the regular grid too, as the resolution to the "should featured items be mixed into the grid instead" question above.

### Ofertas — flip-card redesign, Premium free-slot allowance, and a real booking-lifecycle fix, all this session

**Card redesign:** every Ofertas card (there used to be a visually distinct "featured/hero" treatment for the first card and a smaller "regular" treatment for the rest) now uses one uniform flip-card layout. Tapping a card flips it (a real CSS 3D transform, `.of-flip-inner`/`rotateY(180deg)`, not a modal) — front shows photo + price + progress + Contactar; back shows the business's description and condiciones (terms), both fields the submission form already collected and the DB already stored, just never read back out or displayed by any part of the app until this session. A genuine bug was found and fixed in the process, not just a sizing tweak: the price/discount overlay used a `margin-top:-40px` hack to sit on top of the photo, but its real content was reliably taller than 40px, so the excess spilled below the photo's bottom edge onto the plain card background — reading as a grey block, and varying in severity per-oferta depending on text length, which is why cards looked inconsistently sized. Fixed structurally: the image and its overlay now share a fixed-height wrapper (`.of-hero-wrap`) with the overlay absolutely anchored to that wrapper's bottom edge, so it is now structurally impossible for it to extend past the photo regardless of content length. The image itself was also given more vertical room (130px → 180px) since the original band was too short-and-wide for real photography, cropping brutally.

**Premium free-slot allowance:** a Premium business's first Ofertas submission of each billing cycle is included at no charge; every one after that follows the normal $99 flow. The cycle is anchored to the business's own `premium_since` timestamp (not the calendar month — deliberately, so a business that goes Premium mid-month isn't penalized relative to one that signed up on the 1st), computed by a small `current_oferta_cycle_start()` function that walks forward one month at a time from `premium_since` (relying on Postgres's own month-arithmetic, which correctly clamps month-end overflow, rather than reinventing that edge case). A new `businesses.premium_since timestamptz` column is kept in sync automatically by a trigger (`trg_sync_premium_since`, named to sort alphabetically *after* the pre-existing `trg_prevent_self_premium_update` among `businesses`' BEFORE UPDATE triggers, so it only ever sees the final, post-self-service-block value of `is_premium` for a given statement) — set to `now()` whenever `is_premium` flips false→true, cleared to `null` on the reverse, so a later re-subscription starts a fresh cycle rather than reusing history. Eligibility itself (`oferta_free_slot_available(business_id)`, `SECURITY DEFINER` with an explicit empty `search_path` since `businesses` has no public SELECT RLS policy at all) is the single source of truth, used both as a client-callable RPC (to decide whether to skip the Stripe redirect, and to show "Publica tu oferta gratis" / "— $99" on the Comercio-page CTA button and inside the posting form's own note text) *and* inside the insert trigger itself (`enforce_oferta_free_slot`), which silently coerces `is_free_slot` back to false if the client's belief turns out stale or wrong — so a client-side answer can never actually grant an extra free slot, only mistakenly send someone to pay who didn't strictly need to. **Ordering note, fixed mid-session:** the admin-payment-bypass check originally ran *before* this eligibility check, which meant an admin could never see or exercise the real Premium flow through their own account (always got the generic admin message instead), and — more importantly — meant an admin submitting *on behalf of* a Premium business never actually consumed that business's monthly allowance, a real accounting gap. Reordered so Premium eligibility is checked first regardless of who's submitting; admin bypass is now the fallback for non-Premium businesses or a business that's already used its free slot this cycle. **Known, accepted gap in the backfill:** a pre-existing Premium business ("Maya Tuya") had no historical `premium_since` on record, so it was backfilled to the migration's run time rather than their true original subscription date — meaning their cycle currently starts from that date, not their real anniversary. Corrigible directly in Supabase if the founder supplies the real date from Stripe; not urgent, affects only that one business, one-time.

**Booking-lifecycle fix:** three separate, previously-undiscovered bugs, found while the founder was testing the free-slot feature. (1) `MC.fetchOfertas()` and `MC.fetchMyActiveOfertas()` both only ever checked `status='published'` — neither checked whether the oferta's *booked date* had actually arrived, so an approved-but-future-dated oferta went public (and showed as "active"/confirmable to its own business) immediately instead of waiting its turn. Fixed by filtering both on `postedDs<=TODAY_DS`. (2) Ofertas turned out to be the *one* content type excluded from `SELF_EDIT_TABLES`/`MY_POST_TABLES`, the shared "my submissions, with status and rejection reason" system every other content type uses — meaning a rejected oferta's `rejection_reason` was being saved correctly by the existing generic `moderatePost()` function, but there was no view anywhere that could ever show it to the person who submitted it. This is the actual explanation for "I removed it and got no notification, no message, no way to fix and resubmit" — not a broken removal flow, a missing visibility one. (3) Rejecting an oferta never freed its `ofertas_bookings` row — the booking and the parent oferta row have no cascade relationship at all, so a rejected oferta permanently squatted on its calendar date forever, blocking even the original business from reclaiming the slot they'd already paid for. **All three fixed:** (1) and (2) by adding `MC.fetchMyPendingOfertas()` and a new "Pendientes" tab inside the existing Ofertas activas modal, showing anything not currently live — awaiting moderation ("En revisión"), approved but scheduled for the future ("Programada", with the actual date), or rejected ("No aprobada", with the real reason if one was left) — this is also, incidentally, the fix for (1)'s visibility gap, since a future-dated approval now shows here instead of going live early. (3) fixed with a real DB trigger (`trg_free_oferta_booking_on_reject`, fires on any `status→'rejected'` transition regardless of which code path causes it, tested with real disposable inserts) that deletes the associated booking. **Known, accepted scope limit:** the freed date becomes available to *anyone*, not reserved specifically for the original business for some grace period — a real hold/reservation system would be more precise but meaningfully more complex for what should be a rare case (a genuine rejection, not routine editing — Ofertas still has no self-edit path by design, unchanged from prior versions).

### Randomization — new this session

Mercado and Clasificados previously sorted by `created_at desc` (a real recency bias — the newest seller always led). ### Eventos — filter redesign and a real spacing-bug fix, both this session

Date and category filters converted from chip rows to compact `<select>` dropdowns (`#evt-date-select`/`#evt-cat-select`), matching Mercado's existing filter styling; the colonia input was restyled to the same compact pill treatment Mercado/Clasificados already had (this specific visual restyle was *not* extended to Empleos/Avisos/Reportes/Perdidos's own colonia inputs, which still use the older full-width style — flagged, not yet done). Separately, a real redundant-spacing bug was found and fixed: the event list's flex container used `gap` for spacing between items, but individual event cards *also* carried their own `margin-bottom`, and the per-day group header carried its own top/bottom margin on top of that — all three stacking additively rather than one replacing the others, which is what actually caused "too much space between events" when (as is typical) a day has only one event. Fixed by removing the card's redundant margin entirely and cutting the header's margin down to a small nudge, since `gap` now does the real work; card thumbnails were also bumped from 52px to 64px (matching a size already used elsewhere in the app) for a slightly fuller, "busier" feel per the founder's request. This is the same general *shape* of bug as last session's `.empty` class-collision — a component inheriting spacing designed for a different context — worth continuing to watch for.

### Duplicate detection — new this session, businesses only so far

Confirmed directly against the schema: `businesses` has no unique constraint of any kind on name, phone, or address — nothing stops two accounts from registering what is, in reality, the same business (the founder's own example: business partners each independently creating an account). Compounding factor discovered while investigating: Ofertas' concurrent-slot cap is enforced per `business_id`, so a duplicate business entry doesn't just confuse customers, it independently gets its own fresh cap — a real path to exceeding what someone's actually paying for. Fixed with a duplicate-spotting *aid* at moderation review time (`MC.fetchSimilarBusinesses()` / `renderBusinessDuplicateCheck()` / `fillBusinessDuplicateCheck()`), directly mirroring a pattern that already existed for Eventos (same-day duplicate events, flagged if times are close) but had never been extended to Businesses — surfaces any other business (any status) sharing the submitted phone number (flagged prominently — two genuinely different real businesses essentially never share one) or an overlapping name. This does not block or auto-reject anything; it's information surfaced to the admin before they decide, same as the Eventos version. **Not built, deliberately left as Open Questions:** a submission-volume cap on Reportes (confirmed to have none at all, unlike Avisos' real one-per-day constraint or Clasificados' one-active-at-a-time constraint); anything addressing multi-account abuse via cheap/disposable phone numbers (a real, bounded, hard-to-fully-solve risk at this app's scale, not a code bug); the 5-business Premium cap being per-account rather than per-real-operator (same root cause as the phone-number point).

### Duplicate-badge cleanups — new this session

Two unrelated redundant-badge fixes, both about the same underlying idea (don't show the same actionable status in more places than necessary): the "Ofertas activas" confirm-sale entry point that lived *inside* the per-business "Mi negocio" screen was removed outright (including its now-unnecessary `fetchMyActiveOfertas` call) — the global, account-level "Ofertas activas" entry (three separate badge spots, all account-menu-level, `acct.myActiveOfertas`) is a completely separate code path and was untouched, and remains the one place this shows. ## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0–v8.0 entries below remain valid precedent — new entries from this session follow.)*

- Stale JWT after anonymous→real conversion (`refreshSession()` needed explicitly).
- Owner-update RLS policies with no column restriction are a recurring privilege-escalation shape — fix pattern is a trigger or a `SECURITY DEFINER` RPC doing its own ownership check.
- PL/pgSQL `raise exception` rolls back earlier writes in the same function call.
- `pgcrypto` lives in `extensions`, not `public`, on this project.
- `password_reset_requests` needs an explicit relationship name in PostgREST embeds (two FKs to `profiles`).
- A generic class name reused across unrelated components is a real, recurring bug shape (`.empty` last session; the Eventos gap-plus-margin-plus-margin stacking this session is the same underlying lesson — a spacing/sizing rule designed for one context silently applying somewhere it doesn't belong).
- A trigger that blanket-resets a column on every resident self-edit can silently make a feature permanently unusable without ever throwing an error.
- A third-party host embedded in syndicated content can serve a hotlink-protection placeholder as a normal `200 OK` response.
- `businesses` has no public SELECT RLS policy at all — only owner-or-admin. Any function needing the real state regardless of caller (e.g. this session's `oferta_free_slot_available`) needs `SECURITY DEFINER` with an explicit `search_path`, same reasoning as always, one more concrete instance.
- Google Play requires apps to target Android 16 (API level 36) as of 31 August 2026 (already passed). Verify the packaging tool's current state before a Play Store submission attempt.
- `productos`/`clasificados` still have the deprecated single `image_url` column, unread/unwritten — unchanged, still not urgent.
- **(New)** `enforce_producto_cap` — a real, previously-undocumented hard cap of 10 products for a Premium business, 2 for non-Premium (separate from and in addition to `enforce_producto_promo_cap`'s 2-flagged-item cap from last session). Discovered by hitting it while seeding 20 example products for the Ejemplo business.
- **(New)** `one_aviso_per_person_per_day` is a real DB-level unique index (on `submitted_by, submission_date` where status is pending/published), not just a UI-enforced rule — discovered the same way, while seeding 10 example avisos. Avisos have no expiry/lifespan filter at all (unlike Ofertas' 7-day one), so backdating `submission_date` to satisfy this constraint has zero effect on visibility.
- **(New)** `one_clasificado_per_person` is likewise a real unique index (on `submitted_by`, scoped to pending/published) — a hard lifetime one-active-listing-at-a-time limit per person, confirmed while trying to seed more than one example clasificado.
- **(New)** GitHub Pages' HTTP-level `Cache-Control: max-age=600` (documented in v8.0 as the root cause of the original stale-cache bug, supposedly closed by `updateViaCache:'none'` plus `?forceupdate=1`) can still bite in practice — confirmed directly this session, in a real test, that `?forceupdate=1` did not fully clear a stale cached copy on the first try; a full manual `serviceWorker.getRegistrations()`-unregister plus `caches.keys()`-delete was needed before a genuinely fresh reload showed the real deployed code. Worth remembering that this escape hatch may be less airtight in practice than the code assumes — see Open Questions.
- **(New)** A CSS overlay positioned via negative margin to overlap a sibling element (rather than absolute-positioned within a shared fixed-height wrapper) will spill past that sibling's edge onto whatever is behind it, if the overlay's actual content is taller than the negative-margin value assumes — and the amount of spill will vary per-instance based on content length, which can look like "inconsistent sizing" rather than an obviously-broken layout. The Ofertas price/discount overlay was exactly this shape. If a "text over image" treatment elsewhere in the app uses this same negative-margin technique, it's worth checking whether its content reliably fits the overlap amount.
