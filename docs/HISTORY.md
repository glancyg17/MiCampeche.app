## Core Working Rules

*(All rules from v9.0–v12.0 carry forward unchanged in substance. Concrete reinforcements and one clarified addition from this session below.)*

1. **Always work from the actual current repo.** Reinforced sharply, twice, this session, in a new specific shape: a Claude Code prompt written assuming an EARLIER draft had never been applied — when it actually had — meaning the prompt's own "find this exact text" anchors silently didn't match, and Claude Code had to improvise a merge. The result shipped with two real bugs (a padding/card-width feedback loop; a visibility-timing bug) that were only correctly diagnosed by re-cloning fresh and reading the *actual* current file contents before writing the fix — not by re-reading chat's own prior messages about what it thought it had sent. **The lesson generalizes past "check Supabase" and "check the repo before writing a prompt" to: re-verify immediately before EVERY prompt, even the third in a row on the same feature, even when chat is confident about what an earlier prompt in the same session did — confidence from having written something is not evidence that it matches what's actually deployed.**
1a. Carries forward unchanged.
2. **Verify database/RLS/schema state directly against Supabase before assuming anything.** Used constantly this session — before touching `enforce_producto_promo_cap`/`oferta_free_slot_available`/`enforce_oferta_concurrent_slot_cap`, confirmed via live query that `business_premium_upgrades` genuinely had 2 real rows with `is_premium` still false on the raw column, rather than assuming the bug was theoretical; before designing the unified Premium model, confirmed live that `prevent_self_premium_update` was the actual mechanism blocking self-service, and that `enforce_additional_business_rules` gated on the *primary* specifically, not "any Premium business."
2a. **When testing destructively against live Supabase, don't trust `BEGIN`/`ROLLBACK` alone.** Used throughout — disposable rows, real assertions, explicit post-hoc leak checks after every rolled-back test block, zero leaks confirmed each time, including for the unified Premium slots invariant (blocked/allowed transitions tested exhaustively with disposable accounts before touching real data).
2b. **After ANY DDL that creates a function, run `get_advisors` (security).** Followed for every migration this session (the destacado/oferta-cap fixes, the oferta-edit RLS+trigger, the "Nueva Oferta del día" push infrastructure, the unified Premium slots table+triggers, the example-product promo guard) — one real, useful finding each time it mattered (`notify_oferta_del_dia_if_new` didn't need to be anon/authenticated-executable at all, since only the cron job and the publish-trigger ever call it — revoked, matching the same posture already applied to `notify_push`).
2c. **Proving a trigger fires — or a security gap exists — without sending anything real:** used throughout, with **one new, real test-harness gotcha discovered and worth remembering going forward**: `current_setting('request.jwt.claim.sub', true)` (the dot-path, PostgREST-internal convenience GUC — distinct from `request.jwt.claims`, the JSON blob chat's own disposable tests normally set via `set_config`) is what some existing functions check to decide "is this a real signed-in caller, or an internal/admin context." A disposable SQL test that only sets `request.jwt.claims` — the pattern used successfully everywhere else this project's RLS testing already relies on — will make such a check see `current_setting('request.jwt.claim.sub', true) IS NULL` as true, silently treating the simulated session as privileged/internal regardless of which uid was actually being impersonated. This produced two false "SECURITY FAIL" and "blocked=false" results this session before being caught by noticing the test's own expectations didn't match a careful re-read of the code being tested. **Going forward: any test simulating a real authenticated (non-admin) caller against a function/trigger that might check the dot-path GUC form should set BOTH `request.jwt.claims` and `request.jwt.claim.sub` (and `request.jwt.claim.role` if relevant) to avoid this exact false-positive/false-negative trap.**
2d. **(v13) Before writing a Claude Code prompt for a genuinely novel, hands-feel-dependent interaction — a custom animation, a gesture-driven carousel, anything where "does this feel right" can't be answered by reading the diff — prototype it as a real, interactive artifact and get it validated hands-on first, THEN port the exact validated mechanism to production code.** The Oferta del Día carousel is the clearest example on record: the first two attempts at a "wheel" were each written directly as Claude Code prompts, based on a reasonable-sounding design, and each shipped a real, distinct bug the moment they hit actual code (a CSS feedback loop; a visibility-timing gap) — neither bug was something a careful text-based design review would have caught, because both were specifically about how the mechanism BEHAVES in a real, live, scrolling browser, not about what the code says on paper. The third attempt — built only after the exact infinite-loop mechanism had been dragged, flicked, and stress-tested by the founder as a real interactive HTML prototype (published via the Artifact tool) — shipped clean. The general principle: text-based code review can validate logic; it cannot validate feel, and anything in the second category needs to be built and touched before it's committed to.

## Killed Ideas — Do Not Silently Re-propose

The only things that distinguish today's real oferta now are its starting scroll position and a small "Hoy" ribbon.
- **A linear carousel that stops at real start/end edges.** Built twice (commits `4f8c81c`/`4b2b8eb`), explicitly rejected in favor of a genuinely infinite, looping wheel. Flag before reopening "just make it scroll left-to-right" as a simplification — the founder was specific that continuous looping, not a strip that bounces between two hard stops, is the actual requirement.
- **Admin-mediated (non-self-service) confirmation for Premium slot purchases.** The original $749 flow was built this way on purpose (a real payment, self-granting `is_premium` on the raw column was explicitly treated as too consequential for client-trusted confirmation). Considered directly when unifying the Premium model this session, and resolved the other way: given the founder's explicit "all slots identical" framing and the ALREADY-accepted self-service trust level of the $499/$99/oferta-booking flows elsewhere in this exact app, buying ANY new slot (regardless of price) is now self-service client-trusted, matching the rest of the app's established risk posture rather than preserving the older, more cautious pattern. Flag before reintroducing admin-gating here without a specific, new reason.
- **A reversible "pause" for excess products on a Premium→Básico downgrade.** Considered (matching the app's general philosophy of reversibility over deletion) and explicitly set aside in favor of simplicity: when a business drops from the 10-product Premium cap to Básico's 2, the founder's own instruction was that the owner must choose which 2 stay published — the rest are discarded via the existing, already-built, genuinely-permanent discard flow, not moved to some new paused/hidden state. Building true reversible pausing would have required a new session-local trigger-bypass mechanism (to let a narrow, ownership-checked action set `status='rejected'` without the generic self-edit trigger immediately forcing it back to `pending`) — flagged as a real, buildable option if this ever needs to become reversible later, but not built this session.

### Ofertas — payment messaging, self-edit after rejection

**2026-09-30 — Oferta lifespan removed:** public until sold out or admin-removed; sold-out real ofertas are hidden from public lists (examples still shown with the Agotado ribbon); latest booking date wins when an oferta has several bookings.

**Bug found and fixed: `pickSlotDay()` never checked Premium free-slot eligibility.** The actual submission logic (`submitPost`'s `kind==='oferta'` branch) already correctly checked `oferta_free_slot_available` and skipped Stripe for an eligible Premium business — no one was ever wrongly charged. But `pickSlotDay()`, the function that renders the day-picker's confirmation message and button label the instant a day is tapped, unconditionally showed "$99 MXN" / "Pagar $99 y reservar" regardless of eligibility, purely a display bug. Fixed by having `pickSlotDay()` read a synchronous, already-computed eligibility flag (`selectedOfertaFreeEligible`, set by the existing `applyOfertaBusinessHints()` the moment a business is selected) instead of assuming payment is always required.

**A real, structural gap found and closed: `ofertas` had never had an owner-UPDATE RLS policy in the project's history** — only admin moderation could ever `UPDATE` the table. Combined with the pre-existing `free_oferta_booking_on_reject` trigger (rejecting an oferta deletes its `ofertas_bookings` row, freeing the day back to the calendar), this meant a rejected oferta had no path back to life at all — not a regression, just something that had simply never been built. Added directly in Supabase:
- (schema detail removed; query live Supabase) — an owner-UPDATE RLS policy plus an `enforce_ofertas_edit` trigger now exist; the trigger pins ownership/payment/identity columns and always forces `status='pending'`, same defense-in-depth shape as `enforce_productos_edit`.

Deliberately scoped narrowly, per the oferta form's own existing copy ("no podrás editar esta oferta ni pedir un reembolso después de enviarla"): **only a REJECTED oferta ever gets an edit path.** A live/pending one stays exactly as un-tappable as before — `openMyPostEdit`'s tap-anywhere `editable` computation explicitly excludes the `ofertas` table even though it's now in `MY_POST_EDIT`, so the exclusion only ever lifts via the explicit "Editar y reenviar" button every other rejected content type already has.

**Resubmitting a rejected oferta re-books a fresh day, at no new cost.** Since its old booking was already freed on rejection, the edit form keeps the day-picker calendar visible (unlike every other self-edited content type, where it's irrelevant) and requires picking a new day before the submit button enables — `MC.updateOferta(id, data, newSlotDs)` updates the content fields and inserts a fresh `ofertas_bookings` row at `fee_paid_mxn: 0`, explicitly not a new charge and not consuming another Premium free-cycle slot, since this is a moderation-driven resubmission of something already committed to and already reviewed once. `pickSlotDay()` gained a third branch (alongside the existing free/paid ones) specifically for this edit-mode case: reprogram language, no payment or waitlist copy even on a day that would otherwise show as "full" to a stranger.

Tested end-to-end with disposable data: reject → booking correctly freed → owner self-edits + picks a new day → status correctly forced back to `pending` even when the test payload tried to sneak through `status:'published'` and a different `business_id`/`submitted_by`/`is_premium` → new booking correctly created → a second, unrelated fake user correctly could not touch the row at all.

### Productos — Destacado/Descuento actually saving now, and never on an example

**A real, more serious bug than it first looked: `CONTENT_PAYLOAD.productos` never sent `featured`/`discount_active`/`discount_price` to Supabase at all, on either create or edit.** The form collected them, the DB side (premium check, 2-item cap, discount-implies-featured, all in `enforce_producto_promo_cap`) was completely correct and ready, but the client simply dropped the values before the request ever went out. Confirmed this was silently affecting real submissions, not just a hypothetical — fixed by adding the three fields to the payload builder; the existing DB trigger does the rest exactly as designed, no other change needed.

**A second, independently real bug found while investigating a founder report that this "still didn't work" for a specific business: `business_premium_upgrades` (the self-service $499/mo path for a non-primary business) was recognized by exactly one of four Premium-gated mechanisms** (`enforce_producto_cap`, the 10-vs-2 product count cap) **and NOT by the other three** (`enforce_producto_promo_cap`, `oferta_free_slot_available`, `enforce_oferta_concurrent_slot_cap`) — all three of which checked `businesses.is_premium` directly and had no idea the separate upgrades table existed. Confirmed this was actively affecting two real, currently-paying businesses (`MiCampeche`, `presentame.` — both genuinely enrolled, both with the raw `is_premium` column still `false`). Fixed by updating all three functions to recognize either signal; `oferta_free_slot_available` additionally needed a cycle-anchor date for the upgrade-path case, since `premium_since` only ever gets set for the raw-column path — uses the upgrade row's own `created_at` instead when that's the only source available. **This entire class of bug is now moot going forward** — see Premium Slots below, which retires the two-signal split entirely.

**Example products can never carry Destacado/Descuento, full stop.** Found two real example products (`Mochila para laptop`, `Bicicleta de montaña usada`) carrying both — cleared directly, and `enforce_producto_promo_cap` gained an unconditional `if new.is_example then force everything false` branch at the top, ahead of the premium check, so this can't recur regardless of caller (including admin).

### Mercado — Destacados folded into the main grid (two real bugs found and fixed along the way)

### WhatsApp: Android app choice — confirmed no equivalent exists on iOS

Researched and confirmed before building anything: no website can control which of two installed apps (here, WhatsApp vs. WhatsApp Business) handles a `wa.me`/`whatsapp://` link on either platform via the link itself — that's an OS-level "default app" setting only the person themselves can change, and Android's own disambiguation chooser can't be summoned on demand once a default is set. What Android's Chrome **does** support: an `intent://` link format that can explicitly target one specific installed app by package name (`com.whatsapp` vs `com.whatsapp.w4b`, both real, confirmed names), bypassing whatever default the phone remembers. iOS has no equivalent capability for any app, web or native, to force a specific third-party handler — confirmed via research, not assumed.

Built accordingly, Android-only:
- `isAndroidUA()`/`openWhatsAppSmart(waUrl)` — on Android, shows a small in-app "¿Con cuál WhatsApp?" chooser (two buttons, `navigateWhatsAppPackage` per choice) the first time; the choice is remembered per-device (`localStorage mc_wa_app_pref`, checkbox default-checked) so it only asks once, not on every tap. Everywhere else (iOS, desktop preview), behavior is byte-for-byte identical to before — same plain `wa.me` links, same markup.
- Applies to all three real WhatsApp entry points: `guardedContact()` (the general "Contactar" buttons), `openWhatsAppStep()` (the post-signup/registration confirmation screen), `openVerificationGate()` (the account-under-review screen).
- A new "Qué WhatsApp abrir" row in Preferencias (Android-only, hidden entirely elsewhere) lets the choice be changed or reset to "Preguntar siempre" later.
- Honest limitation, stated plainly: only reliably works in Chromium-based Android browsers (the overwhelming majority of real usage here); a non-Chromium browser or some in-app webviews may not resolve `intent://` at all, degrading to "nothing happens" via the fallback URL, not a crash.

- `notify_oferta_del_dia_if_new()`: the one function both paths call. Broadcasts to every distinct `profile_id` currently in `push_subscriptions` (the first genuinely "everyone subscribed" push in the system, versus every prior trigger's single-target or admin-only shape).
- Fires two ways, so timing can't slip through: a **daily 13:00 UTC cron** (`notify-oferta-del-dia`, 07:00 Mérida fixed UTC-6) catches a booking approved on a prior day whose day has now arrived; a **same-day publish trigger** (`check_oferta_del_dia_on_publish`, `AFTER UPDATE OF status ON ofertas`) catches a business approved on the exact day its own booking is for, without waiting for the next morning's cron pass.
- `notify_oferta_del_dia_if_new()` itself has EXECUTE revoked from `anon`/`authenticated` (only the cron job and the trigger, both running in definer/internal context, ever need to call it) — matching the same lockdown already applied to `notify_push` in v11.
- Tested exhaustively with disposable data on safe future dates (never touching the real "today" row during testing, specifically to avoid accidentally queuing a real push to real subscribers): nothing booked → no push; a real published not-sold-out oferta booked → pushes once, marks itself sent; calling again same day → correctly silent; an example oferta → excluded; sold-out → excluded; still-pending → excluded until approved; the real publish-trigger, when it happens to fire for an unrelated approval on a day that ISN'T today, correctly does nothing.
- **A real, previously-unknown production gap found while building this:** a real oferta ("Un Sitio Web Personalizado," `presentame.`) was already live-booked for the actual day this was built, approved before this infrastructure existed — meaning, under normal operation, it would have quietly never been announced (the day's 07:00 cron slot had already passed before the job existed; the day only gets one natural chance). Deliberately **not** triggered by chat itself — sending a real push to real subscribers is not something chat does unilaterally — left as the founder's own call to trigger manually or let day one start quiet.
- One explicit assumption, stated plainly rather than silently decided: a Premium account's included free-slot oferta counts as equally "real" for push purposes as a $99-paid one — same real business, same real oferta, just a different payment mechanism. Flagged in case the founder wants it narrower.

### Premium Slots — the two-tier model retired, replaced with one unified pool

**The old model, in full, for context:** a raw `businesses.is_premium` column (self-service toggle blocked entirely — `prevent_self_premium_update` let only admin ever flip it), used for exactly one business per profile (whichever was `is_primary`, set permanently at creation with no reassignment mechanism ever built); a separate `business_premium_upgrades` join table (self-service insert/delete, $499/mo), used for every OTHER business. Two genuinely different billing shapes, two genuinely different trust levels, and — per the bugs found and fixed above — two mechanisms that most of the rest of the app had only ever been taught to check one of.

**The founder's own explicit design, confirmed and built exactly as described:** a profile pays for N Premium slots — $749 for the first one ever purchased, $499 for each additional one — and can self-service assign Premium to ANY of its own businesses, instantly, as long as the count of currently-Premium businesses never exceeds N. Turning a business's Premium off always succeeds and instantly frees a slot; turning a different business's Premium on then succeeds too, since a slot is now free — this two-step "off, then on" IS the entire reassignment mechanism, no separate "transfer" action needed. All slots are fully interchangeable once purchased — the $749-vs-$499 distinction is purely about which one happens to be first, not a different tier of capability.

**Two places the founder was explicit the system must NOT auto-decide, both built exactly as directed:**
1. **Cancelling a slot that would leave more Premium businesses than remaining slots is refused outright**, with a message telling the person to turn enough businesses off themselves first — never a silent auto-downgrade of whichever one the system happens to pick.
2. **Turning a business's Premium off when it currently has more than 2 published products** (Básico's own cap, vs. Premium's 10) **requires the owner to explicitly choose which 2 stay published** — a new picker screen blocks the actual toggle until exactly 2 are checked; the rest are discarded via the existing, already-built, genuinely-permanent discard flow (`MC.deleteMyPost`), not silently auto-selected and not made reversible (see Killed Ideas for why reversible pausing was considered and set aside).

**What was built, directly in Supabase, tested exhaustively, then ported to a full client rework:**
- New `premium_subscriptions` table: `profile_id`, `price_mxn`, `created_at` — deliberately **no `business_id` column at all**. A subscription slot is a pure count the profile is paying for, not an object tied to any one business. Self-service owner-insert AND owner-delete RLS (matching the trust level `business_premium_upgrades` already established, not the older, more cautious raw-column pattern — see Killed Ideas).
- `businesses.is_premium` is now the ONLY per-business Premium signal (the old `business_premium_upgrades` table is left in place, unused going forward, deliberately not dropped — historical record, harmless). `prevent_self_premium_update` rewritten from "block entirely unless admin" to "allow turning off unconditionally; allow turning on only while `count(profile's other currently-Premium businesses) < count(profile's premium_subscriptions)`" — admin retains its existing full bypass, unchanged from before.
- `enforce_additional_business_rules` changed from "the PRIMARY business specifically must be Premium" to "the profile must have at least one active Premium subscription" — Principal is fully retired from the Premium model; the column/concept survives only as which business is pre-selected by default when creating a new post, a convenience with zero remaining billing implication.
- **Real data migrated, preserving current state exactly:** Maya Tuya (already `is_premium=true` via the raw column) got one `premium_subscriptions` row at $749; `MiCampeche` and `presentame.` (both genuinely on the old `business_premium_upgrades` path) each got real is_premium=true set directly and a $499 `premium_subscriptions` row apiece. Confirmed live: 3 real slots, $1,747 MXN/month total, matching exactly what the founder is actually being billed.
- **A real, latent bug surfaced specifically by enabling self-service for the first time**: `remind_business_cancellation_on_downgrade` (writes an admin reminder to actually stop the real Stripe charge) was never marked `SECURITY DEFINER`, and had simply never been reachable by anyone but admin before — since only admin could ever flip `is_premium` at all — so its own missing-permission bug was invisible until this session made a genuine non-admin downgrade possible for the first time in the project's history. Fixed to match its own sibling function's (`remind_on_business_premium_upgrade_removed`) already-correct shape. **The general lesson, worth remembering for any future permission-boundary change: enabling a caller path that was previously impossible can surface bugs in code that was written correctly for the ONLY caller that used to exist, and simply never got a chance to break before.**
- A matching reminder trigger exists for cancelling a `premium_subscriptions` row, reusing the existing `'premium_downgraded'` reason. (schema detail removed; query live Supabase)
- **Client-side (`js/app.js`/`js/supabase-client.js`)**: `renderMyBusinesses` (Mis negocios) shows a "N de M espacios Premium en uso" summary plus a "Cancelar un espacio" action, and `renderPremiumToggleAction(biz)` — shared between Mis negocios and the single-business profile view — replaces the old primary-vs-additional split entirely with one consistent per-business action: "Desactivar Premium" (any currently-Premium business), "Activar Premium" (a free instant toggle, if a slot is currently unused), or "Comprar un espacio Premium — $749/$499 MXN/mes" (a real Stripe purchase, priced correctly off the CURRENT slot count) — admin always sees the free instant toggle either direction, matching the database's own unconditional admin bypass. Buying a new slot still returns through the same two existing Stripe links (`premium`/`business_premium_upgrade` markers, unchanged — no Stripe-side reconfiguration needed at all), but both now insert into the unified `premium_subscriptions` table and, if the purchase was started from a specific business's own row, immediately assigns that new slot to it too (one smooth step for the obvious case, falling back to "go toggle it yourself" if that specific assignment fails for any reason).

Tested throughout with disposable data, including the JWT-claim test-harness gotcha documented in Core Working Rules 2c: adding a 2nd business with zero subscriptions correctly blocked, correctly succeeded with one; turning Premium on with no free slot correctly blocked; turning it off then back on a different business (the actual reassignment case) correctly succeeded, instantly, with no payment prompt.

### Comercio / Oferta del Día — a spotlight, arrived at through real iteration

The plain "Comercio" title is gone. In its place: an eyebrow ("Nuevas ofertas cada mañana"), a large Fraunces-serif "Oferta del Día" title (with the accented í continuously, gently wobbling once the title has finished revealing — a specific, deliberate request, isolated to just that one glyph), a one-line subtitle, and — below that — the ofertas themselves, now a single genuinely infinite carousel rather than a static list.

**The path here, worth recording precisely, since it's the clearest example this session of the "prototype live, hands-on, before writing code" principle actually earning its keep (Core Working Rule 15):**
1. Two directional mockups (a full-photo hero borrowing Home's own idiom; a typography-led "stage" with a literal spotlight glow) built as real, interactive HTML and published via the Artifact tool. Founder chose the second, asked for a slower intro and the wobbling í — both added and re-shared as an updated live artifact before being written up as a prompt.
2. First production version (commit `dcb8541`): the approved design, with one enlarged featured card plus a separate list below. Superseded before ever being confirmed live, once the founder clarified the actual requirement was different (see Killed Ideas): one carousel, no size hierarchy, equal treatment for every oferta.
3. Second production version (`4f8c81c`): one carousel, `scroll-snap-align:center`, dynamic scale/opacity based on distance from center — a linear "coverflow" that scrolls to real start/end stops. The founder reported it live as "not centered... still aligned left... cards get narrower on each refresh." **Diagnosed by re-cloning and reading the actual current file contents** (the prompt that produced this had been written assuming an earlier draft was still unmodified — it wasn't) — two real, distinct bugs found: a padding/card-width feedback loop (JS-computed side padding was based on the card's own rendered width, which is itself a function of that same padding — a percentage-based `flex-basis` entangled with the container's own JS-adjusted padding, drifting narrower every render) and a visibility-timing bug (the centering math ran as part of the app's background data refresh regardless of which tab was actually visible, computing against zero dimensions whenever Comercio wasn't the active screen, and nothing ever re-ran it later). Fixed (`4b2b8eb`): card width switched to `vw`-based sizing (stable regardless of the container's own padding, breaking the feedback loop); centering now also explicitly re-runs when `nav()` switches to the `tienda` tab, matching the exact existing precedent `startDestacadosRotation()` already set for this identical class of problem.
4. The founder then clarified the real requirement had never been "coverflow that stops at the ends" at all — it needed to be genuinely infinite, continuous looping. Given two consecutive attempts on this exact feature had each already shipped a real bug once built blind, this one was built and validated as a live, interactive, draggable HTML prototype FIRST (published via the Artifact tool, with a visible on-screen counter confirming the looping mechanism was actually firing) — dragged fast, slow, with momentum, past what would be an edge, by the founder, before a single line was ported to production.
5. **Final, current mechanism (`872d2e1`)**: `renderOfertas()` now renders the real oferta list three times back-to-back (`[...visible,...visible,...visible]`), extracted into a shared `ofertaCardHtml(o)` so all three copies stay in sync with the real flip-card component (flip for details/contact, sold-out ribbon, admin long-press — nothing simplified or duplicated). The wheel opens scrolled into the MIDDLE copy, centered on today's real oferta (or the same random-live-not-sold-out fallback Home's own card already uses) — carrying a small "Hoy" diagonal ribbon (matching the app-wide ¡DESCUENTO!/DESTACADO/Agotado ribbon convention) only on a genuine same-day real release, never on the fallback pick. Once scrolling settles (`scrollend`, with a debounced fallback), if the person has drifted into the left or right copy, the scroll position silently jumps by exactly one copy's measured width, landing on the pixel-identical spot in the middle copy — imperceptible, since every copy is identical content, and the practical effect is a loop that never hits a real end no matter how far or fast anyone scrolls.

**One known, unchanged characteristic, not a new regression:** because `renderOfertas()` fully rebuilds `#of-list` on every background data refresh (not only on an actual tab visit), the wheel re-centers on the day's pick each time that happens, including potentially mid-browse. This was already true of every version built this session and isn't new — worth a dedicated fix (remembering and re-finding whichever card was centered before a rebuild) if it turns out to feel disruptive in real use, not assumed to need one yet.

## Known Real Bugs — Don't Re-diagnose From Scratch

*(All v5.0–v12.0 entries remain valid precedent — new entries from this session follow, marked (v13).)*

- **(v13)** **A UI function can compute the wrong display text/state even when the underlying logic it's describing is completely correct.** `pickSlotDay()` showed $99 payment language to every account regardless of real Premium eligibility, while the actual submission path underneath was already right — nobody was ever mischarged, but the display was actively misleading. Worth checking, for any multi-branch flow, whether EVERY function touching that flow's display (not just the one that finally submits) has actually been taught about all the same branches.
- **(v13)** **A field can be fully built (form UI, DB trigger, cap enforcement) and still never actually persist, if the one function assembling the network payload simply omits it.** `CONTENT_PAYLOAD.productos` never sent `featured`/`discount_active`/`discount_price` at all — every other piece of the feature was correct and ready, waiting for a value that never arrived. Worth a specific check, when a toggle "doesn't seem to save," of the actual payload being sent over the wire, not just the form and the DB in isolation.
- **(v13)** **A permission/feature check can be updated correctly in ONE of several places that all conceptually check "is this business Premium" and silently miss the rest.** `business_premium_upgrades` was recognized by the product-count cap and nowhere else — three other Premium-gated mechanisms had no idea the table existed. When a second way to satisfy the same real-world condition gets added, grep for every existing check of the ORIGINAL condition, not just the one place that prompted the question.
- **(v13)** **A CSS value read back from the DOM and fed into a NEW value for that same property can create a feedback loop that drifts every render, not just once.** `centerOfertaWheel()` read a card's rendered `flex-basis`-percentage width to compute side padding, then set that padding — which changes the container's content-box, which changes what that same percentage-based width resolves to next time. Fixed by sizing the card off something stable and independent of the container's own padding (`vw` instead of `%`). Worth checking, for any JS that measures-then-sets a container property, whether the thing being measured is itself downstream of the very property being set.
- **(v13)** **A render function that runs as part of a background/global data refresh, not only on an explicit user action, can compute against a hidden (`display:none`) element's zero dimensions — and nothing may ever re-run it once the element becomes visible, unless something explicitly does.** `centerOfertaWheel()`'s positioning broke silently whenever a data refresh happened to land while Comercio wasn't the active tab. Fixed by adding an explicit re-run inside `nav()` itself, at the exact moment the tab actually becomes visible — matching an established precedent (`startDestacadosRotation`'s own reasoning) for this exact shape of bug, which should have been applied here from the start.
- **(v13)** **A test harness simulating a real authenticated caller via `set_config('request.jwt.claims', ...)` alone can silently masquerade as an admin/internal context for any check that instead reads `current_setting('request.jwt.claim.sub', true)`** — the dot-path GUC PostgREST sets separately from the JSON blob, which a manual SQL test doesn't populate unless it explicitly also sets it. Produced two false test results this session before being caught. Set both forms together whenever simulating a real non-admin caller against code that might use either convention.
- **(v13)** **Enabling a permission boundary that was previously entirely closed (nobody but admin could ever do X) can surface a real, pre-existing bug in code written for the only caller that used to exist — because it never had a chance to be exercised by anyone else before.** `remind_business_cancellation_on_downgrade` had been missing `SECURITY DEFINER` since it was written, invisibly, because only admin (who bypasses the relevant RLS through other means) had ever been ABLE to trigger it. The moment self-service Premium toggling became possible for the first time in the project's history, this specific gap became reachable and broke. Worth a deliberate check of every trigger/function downstream of a permission change, not just the policy being changed itself.
- **(v13)** **The committed build stamp not matching a fresh hash of the real content is not a one-time, fully-closed incident** — it recurred (see Deploys & Caching), confirmed independently while writing this file, across many commits and multiple separate Claude Code sessions since it was first fixed in v12. The underlying app code was confirmed sound both times (every real test passes when the stale gate itself is bypassed) — but "the last reported `npm test` run said ALL PASSED" continues to not be sufficient evidence on its own. An independent re-clone's own fresh stamp check is the only thing that has caught this, either time.
